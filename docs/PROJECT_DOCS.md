## Данные и права

Prisma schema (`../prisma/schema.prisma`; исходник/артефакт не входит в публикацию) описывает пользователей, проекты, членство, колонки, задачи, сообщения, теги, исполнителей, историю, уведомления, шаблоны, повторения, автоматизации и сохранённые представления.

`Project.ownerId` задаёт владельца проекта. `ProjectMember` содержит роли `MEMBER` и `PROJECT_ADMIN`, `User.globalRole` — `USER` и `ADMIN`. По `src/lib/project-access.ts` участник читает и изменяет задачи, администратор проекта также управляет участниками; владелец и глобальный администратор имеют полные права в этой проверке. Наличие helper не доказывает корректное применение во всех маршрутах — это отдельная проверка.

`Task.columnId` определяет колонку, `ProjectColumn.workflowKey` — её ключ процесса; legacy `Task.status` сохраняется. Для перемещений предусмотрены `rank`, `version`, `boardRevision` и `TaskMoveOperation`. Контракт `/api/tasks/:id/move` включает целевую колонку, соседей, `expectedVersion` и UUID операции. Два DnD-адаптера выбираются через `dndV2Enabled`.

У задачи могут быть несколько исполнителей. Отдельных структур для единственного владельца лида, подтверждения передачи, отчётного периода и почтового ключа импорта в схеме нет. Сначала требуется проектирование этих правил, затем реализация и приёмка.

## Расписание и автоматизации

Шаблоны, повторения и правила уже представлены моделями, API и UI. Процессор правил поддерживает уведомления, теги, изменение приоритета, назначение пользователя, перемещение и комментарий. Работа конкретного правила требует проверки события, условий и последствий.

`POST /api/recurring-tasks/process` обрабатывает наступившие повторения. Он нуждается во внешнем запуске; существование cron в окружении не подтверждено. В handler bearer проверяется только при заданном `CRON_SECRET`; middleware исключает `/api`. До эксплуатации требуется закрыть режим без секрета и проверить параллельный/повторный запуск без дублей.
