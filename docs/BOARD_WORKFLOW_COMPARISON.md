# Доски заявок: как работает сейчас и что меняем

Обновлено 20.10.2026. Это точка входа в описание взаимодействия сотрудников на досках приложения. Доска GitHub Projects используется отдельно для разработки.

- [Как сотрудники работают сейчас](BOARD_CURRENT_WORKFLOW.md) — поведение, найденное в исходниках корневого приложения. Это проверка кода, а не подтверждение работы сервера или успешного сценария в браузере.
- [Как будем работать по согласованным правилам](BOARD_TARGET_WORKFLOW.md) — будущий процесс для сотрудников. Согласование и создание задач не означают, что этот процесс уже реализован.
- [Подробные правила и матрица прав](REQUEST_LIFECYCLE.md) · [Карта реализации](REQUEST_LIFECYCLE_BACKLOG.md).

Сейчас приложение устроено как общая доска участников проекта. Целевой процесс разделяет подачу заявки, работу ответственной группы и личный доступ автора, исполнителя и наблюдателей.

## Главное сравнение

| Область | Сейчас, по прочитанному коду | Согласовано для будущей реализации | Задачи |

Любой участник добавляет любого пользователя системы наблюдателем; тот читает обычную часть, комментирует и прикладывает файлы. Опубликованные комментарии не меняются; исправление — новым сообщением. ## С чего начнём внедрение

Первые доски — [ИТ-заявки, #61](https://github.com/lenremont2/kanban_pochta/issues/61) и [жалобы клиентов, #25](https://github.com/lenremont2/kanban_pochta/issues/25). Начинаем с новых заявок; старую почту пока оставляем справочником. Автоматический импорт не входит в этот первый запуск.

Сначала нужны общий контур прав, работающие вложения и согласованные переходы, затем шаблоны двух досок и [пилот, #10](https://github.com/lenremont2/kanban_pochta/issues/10). По оставшимся решениям — [очередь уточнений](BACKLOG_CLARIFICATIONS_2026-10-20.md): участники и владельцы приёмки пилота, иерархия руководства, численные сроки и календари, частота напоминаний, получатели внутренних уведомлений, хранение удалённого и удаление вложений описания.

Продуктовые задачи остаются открыты до реализации и проверок. Обновление этой документации не переводит их автоматически в «Завершена». Как брать и проверять задачи разработки, описано в [регламенте GitHub Projects](TASK_WORKFLOW.md).
