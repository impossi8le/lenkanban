## 2. Основание запроса и границы подтверждённого

В публичном JS basav2 (`/assets/index-D6dJMzCP.js`, снимок 20.10.2026) обнаружены адрес login-app, восстановление через `GET /api/auth/refresh-from-cookie`, отправка запросов с `credentials: include`, обмен basav2 через `POST /api/sso/login` с `uid`, `token`, `phone`, `point`, redirect и logout. Анонимная HTML-форма login-app содержит login, password, выбор офиса и phone; отправка POST на `/login`.

Это наблюдение клиентского кода и формы, а не подтверждённый контракт для подключения нового приложения. Поддержка OIDC/SAML, серверная проверка пароля через LDAP, подписи/TTL токенов и правила cookie не установлены. Cookies, реальные токены, пароли и клиентские данные в пакет не включаются.

Нельзя копировать сессию basav2, принимать присланный браузером uid как доказательство личности или подключать Ленканбан к чужому exchange endpoint без разрешённого контракта.

### Технологическое уточнение к запросу

Основание — [перечень технологий от заказчика](reference/TECH_STACK_PROVIDED_2026-10-20.md); разбор фактов и гипотез — [оценка стека](SSO_STACK_ASSESSMENT.md). Версии из перечня просим подтвердить по развёрнутым сборкам и lock-файлам.

Приоритет запроса — существующий Laravel/JWT/cookie контракт. JWT не подтверждает OIDC; Sanctum не подтверждает, включён ли cookie или bearer режим; MySQL/Redis не устанавливают источник истины сотрудников. LDAP, Passport, Socialite, Keycloak и SAML не считать установленными только по перечню пакетов.

**Получаем конкретно под этот стек:**

| Сервис | Материалы для подключения и test-копии |

| basa-backend PHP8.1/Laravel9/Sanctum3 | Только приём /api/sso/login, profile/logout, guard/middleware и режим Sanctum; DTO/OpenAPI, внешний↔локальный user ID. Не вся CRM |

Не запрашиваем полную копию CRM, телефонию, ClickHouse или платёжные сервисы без доказанной зависимости SSO. MySQL тестового IdP остаётся отдельной от PostgreSQL Ленканбана. Нельзя переносить Laravel guard или общую cookie в наш backend вместо согласованной валидации личности.

## 3. Что передаём мы до регистрации клиента

`<TO_CONFIRM>` означает незаполненное поле, а не готовый адрес/секрет. Домены, callbacks и сроки согласуются; наличие NextAuth не означает, что SSO-адаптер уже существует.

| Параметр | Что отправляем |
| --- | --- |
| application_name | Ленканбан |
| application_type | Серверное веб-приложение Next.js/NextAuth; браузерный UI и отдельный Socket.IO |
| environment | Сначала dev/test; production регистрируется отдельно |
| owner / technical_contact | `<TO_CONFIRM>`: ФИО/роль, рабочий канал связи |
| app_origin_test / app_origin_prod | `<TO_CONFIRM>`: полные HTTPS origins |
| redirect_uris_test / redirect_uris_prod | `<TO_CONFIRM>`: точные callbacks после выбора адаптера, без wildcard |
| post_logout_redirect_uris | `<TO_CONFIRM>`: разрешённые адреса возврата |
| saml_sp_entity_id / acs_url / slo_url | `<TO_CONFIRM>`, только если выбран SAML; предоставим SP metadata после согласования |
| outbound_ips / VPN / DNS | `<TO_CONFIRM>`: откуда сервер обращается к IdP; требования доступа из браузеров отдельно |
| allowed_users / allowed_groups | `<TO_CONFIRM>`: согласованный состав пилота и фильтр допуска |
| requested_attributes | Постоянный ID, логин, отображаемое имя, email при наличии, активность/блокировка, группы/подразделения |
| proposed_group_mapping | `<TO_CONFIRM>`: группы → права приложения; внешний атрибут сам по себе не выдаёт ADMIN |
| access_revocation_max_seconds | `<TO_CONFIRM>`: согласованный верхний предел отзыва для HTTP, API-токенов и открытых Socket.IO |
| test_host / resources / DB hosting | `<TO_CONFIRM>`: наша среда либо sandbox подрядчика |
| secret_delivery / recipients | `<TO_CONFIRM>`: защищённое хранилище и уполномоченные получатели |

Мы не передаём доменные пароли сотрудников для регистрации клиента. Client ID выдаёт сторона IdP; у SP entityID в SAML другой смысл — эти поля не взаимозаменяемы.

## 4. Что получить: контракт выбранного протокола

Обязательный минимум для любого варианта: протокол/версия, тестовый адрес и схема входа, идентификатор нашего приложения, способ серверной проверки идентичности, стабильный ID и профиль атрибутов, тестовые пользователи, отзыв/выход, сетевые требования и технический контакт. Для отсутствующей функции — явное ограничение и согласованная альтернатива.

Собственный Laravel/JWT/cookie flow рассмотрен в 4.3; разделы 4.1–4.2 заполняются только при подтверждённой поддержке соответствующего стандарта.

### 4.1. Если OpenID Connect

| Параметры ответа | Требуемая конкретика |
| --- | --- |
| issuer / discovery_url | Точные значения для test и prod; discovery JSON, если поддерживается |
| authorization_endpoint / token_endpoint / jwks_uri | Адреса и методы; допустимые алгоритмы подписи, выбор по kid, ротация ключей |
| userinfo_endpoint | Адрес, авторизация и схема ответа; если отсутствует — какие claims выдаются в ID token |
| client_id / client_type / token_endpoint_auth_method | Регистрация Ленканбана; confidential/public и способ аутентификации клиента; secret или private key по защищённому каналу при необходимости |
| grant_types / response_types / PKCE | Поддержка Authorization Code, PKCE S256; требования state/nonce; unsupported указать явно |
| redirect_uris / post_logout_redirect_uris | Точные зарегистрированные значения, отдельно test/prod |
| scopes / claims / audience | Согласованный минимум; subject и issuer; email/email_verified при наличии, name, groups, department, active/disabled; типы, nullable и источник каждого поля |
| token/session TTL | Время жизни ID/access/refresh и SSO-сессии, idle/max TTL, clock skew; refresh rotation и replay policy, если refresh поддерживается |
| logout / revocation | end_session_endpoint, front/back-channel logout, revocation/introspection endpoints — только если поддерживаются; чем заменяется отсутствующая функция и как достигается срок отзыва |
| errors / limits / example | Коды ошибок, timeouts/rate limits, минимальная последовательность запросов и синтетические примеры claims без рабочих токенов |

Не требуется выдавать все перечисленные endpoints, если они опциональны для выбранного профиля. Требуется достаточный и проверяемый контракт и явный перечень отсутствующего.

### 4.2. Если SAML 2.0

- IdP entityID и XML metadata/metadata URL с порядком обновления; SSO/SLO endpoints и поддерживаемые bindings.
- Публичные X.509 сертификаты подписания, сроки/ротация; требования подписания Response/Assertion/AuthnRequest и шифрования. Закрытые ключи IdP не запрашиваем.
- Согласованные SP entityID, ACS, SLO, Audience, Recipient/Destination; допустимый clock skew, validity window и replay policy.
- NameID format и стабильность, карта атрибутов сотрудника/групп, nullable/multivalue, синтетические примеры.
- SP-initiated/IdP-initiated flow, RelayState, InResponseTo, ошибки, logout и способ отзыва действующих сессий.

### 4.3. Если собственный SSO/API

- Версионированная документация/OpenAPI: login/start, callback, exchange/validate, profile, refresh, logout/revoke; endpoint, HTTP method, content-type, поля/типы/обязательность, успешные и ошибочные ответы.
- Как зарегистрировать отдельного клиента Ленканбан: client identifier, серверные credentials, callback allowlist и допустимые origins; выдача отдельной test-регистрации.
- Схема доверия: подписанный ответ либо аутентифицированная серверная проверка opaque code/token. Указать issuer/audience/client binding, TTL, одноразовость, защиту replay, подмены uid, login CSRF и open redirect.
- Уточнить назначение `uid`, `token`, `phone`, `point`, обязательность для нового клиента и источник их значений; token из URL не считать долгоживущим секретом. Запросить поддерживаемый вариант одноразового обмена.
- Кто устанавливает cookies, Domain/Path/Secure/HttpOnly/SameSite, сроки, cross-origin/third-party ограничения браузеров, CORS с credentials, CSRF и refresh/logout. Не предлагать общий доступ всех приложений к сессионному секрету.
- Контракт profile/validation: постоянный внешний ID, атрибуты, группы/подразделения, active/locked, дата/версия изменения; серверный отзыв и статус при недоступном IdP.
- Если текущий механизм предназначен только для basav2, запросить отдельный поддерживаемый адаптер/шлюз, объём и сроки его предоставления.

### 4.4. LDAP только при подтверждённом выборе

Если IdP использует LDAP, это само по себе не требует прямого LDAP-доступа Ленканбана. Если SSO-клиент невозможен и согласован прямой LDAP, дополнительно получить: тип/версию каталога, LDAPS/StartTLS endpoints и CA, Base DN, search filters, login/stable ID/group/department/disabled attributes, nested groups policy, read-only service bind при необходимости, timeouts и тестовый каталог. Запретить незашифрованный fallback. Реальные service secrets передать защищённо.

## 6. Тестовая БД пользователей и набор сценариев

Нужна отдельная обезличенная копия или синтетический набор, который действительно обслуживается тестовым SSO. Если пользователи находятся в LDAP/внешнем IdP, одной SQL-БД недостаточно: предоставить test-directory/tenant, схему идентичности и способ создать там пользователей.

**Комплект:** СУБД и точная совместимая версия, схема/DDL и миграции, формат/версия дампа либо fixtures/seed, контрольная SHA-256 сумма архива, команды восстановления/инициализации/сброса, требуемые DB privileges, словарь полей и связей. Указать количество пользователей/групп/подразделений и способ повторного создания.

В fixtures сохранить форматы ID и целостность user↔group↔department↔office внутри тестового набора; реальные идентификаторы и персональные данные заменить синтетическими согласованными значениями. Нужны отдельные примеры null email, multivalue groups, нескольких подразделений и неактивной записи.

**Не включать:** реальные пароли/парольные хеши, действующие сессии, refresh/access/API tokens, MFA seeds/recovery codes, private keys, production client secrets, реальные телефоны/email/ФИО и клиентские заявки. Для тестового входа создать новые credentials через seed/IdP test-directory; сами значения передать защищённо. Если test-пароль генерируется при запуске, описать эту процедуру.

| Тестовая личность/сценарий | Что должно быть возможно проверить |
| --- | --- |
| Обычный сотрудник | Вход, стабильный ID, профиль, только согласованные группы |
| Руководитель / несколько подразделений | Корректный набор групп без автоматического расширения прав приложения |
| Администратор тестового IdP | Управляемое изменение fixtures; не означает ADMIN в Ленканбане |
| Disabled / locked / удалённый | Отказ нового входа и отзыв уже открытых сессий по согласованному сроку |
| Сотрудник вне разрешённой группы | Отказ доступа независимо от успешной аутентификации в IdP |
| Смена логина/email/ФИО | Сохранение постоянного ID и привязки к существующему аккаунту |
| Удаление/добавление группы | Обновление прав и отзыв доступа, если группа допуска удалена |
| Повторный callback / истёкший ответ | Проверки TTL, audience, replay и ошибок обмена |
| IdP недоступен / восстановлен | Контролируемый отказ/восстановление без обхода политики; аварийный локальный администратор приложения проверяется отдельно |

Для blocked/deleted/renamed сценариев дать исходные записи и инструкции смены состояния/сброса. Не выдавать всем тестовым сотрудникам административные права ради удобства.

## 8. Приёмка ответа и возобновление работ

- [ ] Выбран один реальный способ интеграции; LDAP/OIDC/SAML не предполагаются по внешнему виду формы.
- [ ] Наш клиент и test callbacks согласованы; каждый `<TO_CONFIRM>` из минимального пути заполнен либо имеет обоснованную альтернативу.
- [ ] Есть документированный обмен и серверная проверка личности, постоянный ID и согласованные claims/группы; привязка существующего пользователя не выполняется только по совпадению email.
- [ ] Копия SSO воспроизводимо запускается с новой тестовой БД/каталогом либо доступен эквивалентный sandbox; данные восстанавливаются/сбрасываются по инструкции.
- [ ] Из нашей среды проверены DNS/TLS/CA/сеть и тестовый вход; ошибки, expiry/replay, смена профиля/групп, блокировка и logout проверены отдельно.
- [ ] Подтверждён максимальный срок отзыва доступа для HTTP, API и Socket.IO; отключение сотрудника не оставлено только до очередного входа.
- [ ] Секреты получены через согласованный канал; в Git/issue остаются только ссылки и результаты без секретов/персональных данных.

После ответа: заполнить параметры в этом документе без секретов → разобрать пробелы в #12 → поднять копию/sandbox и проверить контракт → реализовать выбранный адаптер/привязку в [#13](https://github.com/lenremont2/kanban_pochta/issues/13) → проверить отзыв HTTP/API/realtime и аварийного администратора в [#14](https://github.com/lenremont2/kanban_pochta/issues/14). Начальные названия LDAP-задач не предрешают выбранный протокол.

#12 не закрывать только по получению письма: необходимы проверяемый контракт и соединение из целевой test-среды. Незаполненные обязательные значения, отсутствие прав на копию или невозможность серверной проверки ответа — вопросы подрядчику, а не повод придумывать реализацию. Production rollout и его дата согласуются отдельно.

## 9. Справочные стандарты

Поля OIDC уточняются по [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html); требования защиты OAuth-обмена — по [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html). Эти стандарты служат шаблоном вопросов, но не доказывают их поддержку login-app. Корпоративный контракт и версию должен подтвердить подрядчик.

Оформленный пакет для отправки и форма ответа: исходный Markdown (этот документ; готовый PDF не публикуется). Полный технический контракт и условные приложения сохраняются в этом Markdown.
