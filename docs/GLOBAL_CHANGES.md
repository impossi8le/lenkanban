## 3. Общие статусы и поведение

- Это правило распространяется на обе указанные таблицы и на все остальные.
- Полный перечень статусов пока не задан; отдельные статусы для этих таблиц не придумывать.
- Дополнение по последнему примеру: добавить в общий набор статус/колонку «Ждём сотрудника». Точные условия перехода и соответствие ранее согласованному состоянию «На уточнении» уточнить перед реализацией.
- Добавить в общий набор статус/колонку «Решено» по новому примеру. Соответствие существующему состоянию завершения согласовать при реализации общего маршрута.

## 5. Кнопка добавления обращения

- Изменить текст кнопки «Новая задача» на «Добавить обращение».
- Сделать красный вариант оформления этой кнопки.

## 6. Упростить карточки обращений

- Убрать из видимой карточки короткие технические коды вида «#Z0VY», «#YXKS», отмеченные стрелками на первом скриншоте: пользователю это лишняя информация, усложняющая понимание.
- Это требование к отображению карточки, а не к удалению идентификаторов из данных.

## 7. Время ожидания новых обращений

- В разделе новых обращений (на первом скриншоте — колонка «Новая», в пояснении пользователя — «НОВЫЕ») показывать на карточке, сколько времени назад поступило обращение.
- Использовать понятное относительное время, например «4 мин назад», по примеру второго скриншота.
- Цель: сотрудники должны видеть, какие обращения дольше ждут и какие нужно активнее брать в работу.
- Автоматическая сортировка и дополнительные правила приоритета этим требованием пока не заданы.

## 8. Взятие обращения в работу и данные автора

- Для пользователей-исполнителей, в частности сотрудников техподдержки, показывать на карточке доступного им нового обращения кнопку «Взять в работу» по примеру на скриншоте.
- Нажатие назначает текущего сотрудника исполнителем и переводит обращение в работу по общим правилам процесса.
- На карточке показывать имя человека, оставившего обращение, и отдел, в котором он работает.
- Визуальный ориентир из дополнительного скриншота: данные автора отдельным блоком под заголовком; действия и сведения об исполнителе — в нижней части карточки. Внешний вид приблизительный, не требование точного копирования.
- Пока исполнитель не назначен, внизу слева показывать «⌛ Ждёт специалиста», справа — кнопку «Взять в работу →».
- Уточнение по последнему скриншоту: кнопку взятия в работу показывать при наведении мышью на карточку, а не постоянно. На примере короткая подпись «Взять»; действие остаётся тем же — «Взять в работу».
- После взятия в работу вместо приглашения взять обращение показывать назначенного исполнителя: имя и роль/должность, например «Алексей (Сисадмин)», с зелёным выделением по примеру. Кнопку «Взять в работу» для уже назначенного обращения убрать.
- Дополнение пользователя: автору обращения и другим пользователям с доступом к карточке должно быть явно видно, что специалист ещё не назначен, либо кто именно взял обращение в работу — чтобы понимать, кого ждать. Кнопка взятия в работу при этом доступна только исполнителям с соответствующими правами.
- Использовать пример без хештегов и кодов вида «#IT-108», с учётом требования об упрощении карточек.
- Остальные детали примера (категория, рабочее место, AnyDesk и другие поля) отдельно не утверждены. Срочность уточнена в пункте 10.

## 9. Убрать перетаскивание карточек между столбцами

- Убрать с карточек отмеченную на скриншоте ручку перетаскивания (значок из точек).
- Отключить возможность захватывать и перетаскивать карточки из одного столбца в другой, включая захват за другие участки карточки.
- Изменение статуса выполнять через предусмотренные действия общего процесса, в том числе кнопку «Взять в работу» из пункта 8.

## 10. Два уровня срочности и быстрый фильтр

- Для обращений оставить только два уровня срочности: «Срочно» и «Не срочно».
- Убрать из пользовательского выбора остальные градации приоритета, включая «Средний»: пользователю достаточно различать срочные обращения и те, которые могут подождать.
- По примеру добавить переключатель фильтра «Все / Срочные»: «Все» показывает обращения обоих уровней, «Срочные» — только срочные обращения в доступной пользователю области.
- Срочность — отдельный признак обращения, а не рабочий статус.
- Правило перевода существующих приоритетов в два уровня пока не задано; не менять данные при сборе требований.
- Для «Претензий клиентов» пользователь уточнил название признака: «Уровень опасности клиента» вместо обычной срочности. Не вводить дополнительные градации без согласования.

## 11. Основной образец дизайна и светлая тема

- Пользователь предоставил готовый HTML-макет как основной визуальный ориентир: `support_board_v5.html` (исторический локальный макет, не входит в публичный репозиторий).
- Использовать именно этот общий стиль интерфейса; из макета можно переиспользовать подходящие решения оформления и компоновки.
- Интерфейс должен быть простым и сразу понятным обычным сотрудникам, включая пожилых: хорошо читаемые надписи, заметные действия, крупные элементы и понятное расположение информации.
- Светлая тема — по умолчанию. Ориентир макета: светлый фон, белые карточки, контрастный текст, отчётливые границы и цветовые акценты.
- Левое меню адаптировать под ранее записанные требования, а не копировать целиком: раздел «Запросы в отделы», направления «Техподдержка и ИТ» и «Претензии клиентов». Дополнительные отделы из макета этим сообщением не добавляются.
- Ранее согласованные требования сохраняются при использовании макета: красная кнопка «Добавить обращение», отсутствие технических кодов на карточках, отключённое перетаскивание между столбцами, два уровня срочности. Отличающиеся подписи, цвета и поведение демонстрационного HTML автоматически эти решения не заменяют.
- По отдельному запросу пользователя создан производный автономный HTML-прототип для оценки; исходные пользовательские макеты и основное приложение не изменяются на этом этапе.

## 12. Претензии клиентов: форма, карточка и ссылка на заказ

- Дополнительный образец: `boards_v6.html` (исторический локальный макет, не входит в публичный репозиторий). Сохранять общую структуру и стиль техподдержки; для претензий менять подходящие тексты и поля, а не создавать отдельный несовместимый процесс.
- Форма «Новая претензия клиента» по примеру: вид претензии («Цена», «Опоздание», «Повторный брак», «Грубость», «Качество»), номер заказа, телефон клиента, имя клиента, «Чего хочет клиент» и краткое описание случившегося. Обязательность полей пока отдельно не задана.
- В претензиях вместо обычной срочности использовать понятие «Уровень опасности клиента»; пример пояснения в форме — «Клиент грозит отзывом, жалобой или судом». Точные подписи вариантов пока не заданы; дополнительных уровней не придумывать.
- Чек-лист внутри претензии и связанный с ним прогресс из макета пока не включать: пользователь просит сделать проще.
- На карточке претензии показывать номер заказа, телефон и данные клиента по примеру макета, чтобы нужные сведения были сразу видны пользователю с доступом к обращению.
- Номер заказа сделать кликабельной ссылкой на заказ в CRM. Шаблон, предоставленный пользователем: `https://basav2.lenremont.com/requests/{номер_заказа}`. Синтетический пример: заказ `1234567` → `https://basav2.lenremont.com/requests/1234567`.
- Номер заказа — полезные данные обращения; требование убрать короткие технические коды карточек из пункта 6 его не исключает.
- Демо-данные, отдельные SLA, обязательный выбор итога при закрытии и другие дополнительные механики HTML сами по себе не становятся требованиями.

## 13. Тёмная тема и проверка UI/UX

- Добавить полноценную тёмную версию всех экранов прототипа и переключатель «Тёмная тема / Светлая тема».
- Светлая тема остаётся по умолчанию; явный выбор пользователя сохраняется после перезагрузки.
- Подготовить повторяемую автоматическую проверку UI/UX, чтобы после новых правок агент мог заново проверить роли, формы, действия, темы и разные размеры экрана, сохранить скриншоты и отчёт.
- Автопроверка отдельного HTML не является проверкой основной разработки. После внедрения повторить сценарии на разрешённом тестовом стенде приложения.

## 14. Уведомления — основной функционал

- Сохранить заметный пункт «Уведомления», колокольчик и счётчик непрочитанных.
- Уведомление открывает соответствующее доступное пользователю обращение; прочтение отражается в счётчике. Добавить просмотр непрочитанных и «Прочитать все».
- Сохранить уведомления браузера и совместить новый интерфейс с уже реализованной логикой: существующие `notification:new`, колокольчик, `useBrowserNotifications` и `src/lib/browser-notifications.ts`.
- Не создавать второй поток событий или дублирующиеся системные уведомления. Сохранять изоляцию пользователей, права, повтор без дублей и отзыв доступа.
- Реализация браузерных уведомлений в текущем коде рассчитана на открытую вкладку; работу при закрытом браузере не объявлять реализованной без отдельной проверки/реализации Web Push.
- В автономном прототипе лента и события демонстрационные. Кнопка проверки браузерного уведомления запрашивает разрешение только по явному нажатию, не при открытии страницы; отказ не мешает колокольчику.

## 15. Сворачиваемое левое меню

- Добавить кнопку сворачивания/разворачивания боковой панели.
- В свёрнутом виде оставить иконки, активный пункт и счётчики. Названия доступны при наведении и для вспомогательных технологий.
- Запоминать выбранный вид меню. Колокольчик в верхней панели остаётся доступным независимо от бокового меню.
- На узком экране обеспечить удобную адаптацию; в текущем примере меню сверху, подписи сохраняются.

## 16. Скорость — главный критерий

- Скорость загрузки и отклика интерфейса — основной критерий при реализации всех изменений, наравне с сохранением корректного поведения и прав.
- Найти и учесть уже внесённые оптимизации; не потерять их при переносе нового дизайна. Само упоминание прежних оптимизаций не подтверждает текущую скорость.
- Перед внедрением снять исходные замеры основного приложения, после — повторить в сопоставимых условиях: первый вход, повторное открытие, переходы между разделами, открытие карточки/формы, поиск, фильтры и уведомления.
- Проверять не только пустой HTML, но и реальные разрешённые тестовые наборы данных: сетевые запросы, размер загружаемого кода, лишние повторные загрузки, блокировку главного потока и повторные отрисовки.
- Сохранять полезное кэширование и realtime, устранять дублирующиеся запросы/подписки; тяжёлые части загружать по необходимости. Не ускорять за счёт отключения уведомлений, проверки прав или корректной обработки ошибок.
- Фиксировать фактические показатели до/после, условия измерений и ограничения. 61 функциональная проверка HTML не является измерением производительности продукта.

- Существующие ограничения на рабочую БД, публикацию, биллинг и изменения аккаунтов сохраняются; эта инструкция не заменяет отдельное разрешение на такие действия.
