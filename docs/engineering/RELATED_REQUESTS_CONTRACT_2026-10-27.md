# Связанные обращения — решение пользователя27.10.2026

Пользователь подтвердил: связь взаимная; А–Б и Б–В образуют общую группу А–Б–В. При удалении прямой связи группа пересчитывается. Менять связи могут автор, текущий исполнитель и руководство с соответствующим правом изменения. Наблюдение или чтение само по себе такого права не даёт.

## Поведение

- В карточке отдельный раздел «Связанные обращения»: тема, отдел и состояние доступной карточки, переход в неё. Добавление через поиск доступных обращений или ссылку на карточку этого приложения.
- Храним прямые неориентированные связи, а не копии всей группы. Повтор/цикл не создаёт дублей. Связь с собой запрещена. Удаление убирает только выбранную прямую связь и не удаляет обращения, файлы или переписку.
- Прямые связи доступны для удаления при разрешённом управлении. Косвенная связь помечена «Через другое обращение», её нельзя ошибочно удалить как прямую: для изменения нужно открыть промежуточную карточку.
- Связь не назначает исполнителя, не меняет отдел/статус/срок/получателей/наблюдателей и не открывает доступ. Это не перенос между досками и не зависимость «блокирует выполнение».

## Доступ и данные

- Все readers/search/files/history/realtime продолжают использовать общий серверный ACL. В связанных карточках показываются только доступные пользователю обращения.
- Обход графа идёт только через доступные вершины: скрытое персональное обращение не становится мостом к другим карточкам. Не выдавать скрытые ID, заголовки, числа или маркеры существования.
- Для изменения нужна свежая проверка права управления исходным обращением и чтения выбранной карточки. Изменение хранится общей version/CAS/idempotency/Activity-моделью; транзакционные блокировки упорядочены, повтор не создаёт второй связи/истории.
- История добавления/удаления в обеих карточках не раскрывает недоступный второй конец связи. Realtime не передаёт названия/ID скрытых соседей: клиент перечитывает разрешённую проекцию.
- Диагностика только в существующем формате, без тем, описаний, поисковых строк и ссылок пользователя. Тексты ошибок объясняют, как найти доступную карточку, без подтверждения существования закрытой.

## Контракт UI/API для параллельной работы

`GET /api/tasks/:id/related` → `{ taskId, version, canManage, items: [{ id, title, projectId, projectName, state, isDirect, url }], limited }`. `items` содержит только доступную связную компоненту без текущей карточки; сортировка стабильная, прямые прежде косвенных. Ограничение обхода должно быть явным, без скрытого общего счётчика.

`POST` и `DELETE` того же маршрута: `{ operationId, expectedVersion, relatedTaskId }`. Ответ — свежая разрешённая проекция того же вида. Использовать существующие API error/no-store/origin/receipt правила. Публичный поиск `/api/tasks?search=…` уже проверяет ACL; UI не кеширует результаты между аккаунтами. Новый компонент `TaskRelatedRequests` получает `taskId`, `version`, `actorId`; root интегрирует его в карточку после готовности backend.

Приёмка: А–Б–В, цикл/повтор, удаление мостовой связи и сохранение оставшихся связей, чужие/наблюдатель/отозванные права, скрытый мост, прямой URL, история, обновление второй сессии и перезагрузка. Это требования; документ не подтверждает реализацию или выкладку.
