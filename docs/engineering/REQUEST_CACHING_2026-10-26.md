## Единая политика кеша

1. Кеш React Query действует в памяти одной учётной записи. При смене actor или глобальной роли создаётся новый QueryClient; старые запросы отменяются, старый кеш и локальные приватные состояния дочернего интерфейса очищаются. Обычное обновление сессии того же сотрудника сохраняет тёплый кеш.
2. Обычные чтения: staleTime 60 с, неактивный кеш 5 минут. Справочники projects/project/columns/tags/members/saved views/templates/automation/recurring — staleTime 5 минут. Это верхние окна переиспользования; существующие более строгие настройки конкретного запроса сохраняются. Мутации и realtime инвалидируют данные; reconnect восстанавливает пропущенные изменения. Отзыв доступа очищает защищённые данные существующим общим механизмом.
3. Сервер заново проверяет текущую учётную запись и ACL. Решения о правах, версия для команды, lifecycle capabilities, токены и результаты авторизации не переводятся в общий кеш роли. HTTP `no-store` защищённых API сохраняется; публичные чанки сборки используют существующий immutable-кеш.
4. Однозначные отказы 4xx и отменённые чтения не повторяются автоматически. Сетевые/серверные сбои имеют максимум два повтора. Автоматические повторы мутаций отключены.
5. Запросы чтения принимают AbortSignal. Закрытие/смена ключа отменяет ненужный запрос, когда у него не остаётся активных наблюдателей. Отмена fetch не доказывает отмену уже исполняемого SQL. Мутации с неизвестным результатом сохраняют прежний протокол идемпотентности.

## Применённые изменения интерфейса

- Список участников: один canonical DTO `{owner,items}` под `project-members`; фильтры таблицы/календаря получают массив через observer select. Они больше не считают объект массивом. Одновременные потребители используют один GET. События membership согласованно инвалидируют canonical и legacy кеши.
- Открытие карточки: защищённое чтение начинается по клику параллельно с загрузкой кода редактора. Hover/focus прогревает только код. Каждое открытие имеет новый actor/project/task/openId и свежую серверную проверку; закрытие удаляет этот кеш. Ошибка предзагрузки не вызывает второй автоматический GET при появлении lazy-компонента; повтор доступен явно.
- Поиск: работает только в открытом окне с авторизованным сотрудником, ключ включает actor; устаревшие запросы отменяются без уведомления об ошибке отмены. Результат хранится 15 с, неактивный кеш 60 с. Проекты запрашиваются в лёгком режиме navigation без ненужных подсчётов задач; отсутствующий счётчик не показывается как фиктивный ноль.
- Действия с заявкой: после подтверждённой мутации свежие lifecycle capabilities загружаются сразу, параллельно со списком и историей. Только актуальные capabilities задерживают следующую команду. Медленная история не блокирует действия. При отказе свежего чтения предлагается повтор чтения без повторной отправки сохранённой команды. Закрытие использует одно подтверждающее чтение.
- В 27 queryFns основных экранов передаётся signal без изменения URL/DTO/ключей и мутаций. Отдельные неактивные/диагностические/непринадлежащие задаче потребители перечислены в инвентаре.
- Холодный старт: защищённое содержимое основного раздела монтируется после определения identity, чтобы запрос не запускался сперва в anonymous client и повторно после его замены. Публичные шапка/меню и Главная отображаются сразу. Обновление сессии с уже известным actor не блокирует тёплый интерфейс.

## Полнота аудита и ограничения

Аудит API: 95 route-файлов, 55 явных GET. Аудит клиента: 54 прямых query hooks, 15 callers pager, 128 сетевых call sites, 78 групп endpoint expressions. Call sites не равны запросам на один экран. Матрицы и исходные hashes сохранены в `work/request-cache-audit-20261026/api-inventory.json`, `api-cache-matrix.md`, `client-inventory.json`, `client-findings.md`.

Общий ответ по одной роли непригоден для приватных задач, уведомлений, поиска, внутренних сообщений и файлов: одинаковая роль не означает одинаковую видимость. Для общего серверного кеша стабильных данных потребуются свежий gate, версия и инвалидация всех writers; механическое увеличение TTL не заменяет эту работу. Не кешировать side-effectful GET verify-email, отказы доступа и устаревшие capabilities.

Сохраняются известные следующие кандидаты: ограничить объём messages/threads; сократить повторное перечитывание истории чата при join/reconnect с сохранением catch-up; объединить пересекающиеся detail refresh; убрать ненужный RSC round trip при открытии формы. Не объявлять эти предложения выполненными. Два несогласованных локальных drift-файла members route/dialog не включаются в публикацию этой задачи.

Тесты с моками проверяют поведение кеша, отмену, свежесть прав и порядок действий; они не являются замером production UI. Сборка/QA/выкладка и ограничения браузерной проверки фиксируются отдельным отчётом.

Для обслуживания статистики и оценки JIT использованы официальные контракты PostgreSQL: [ANALYZE](https://www.postgresql.org/docs/current/sql-analyze.html), [выбор JIT по стоимости плана](https://www.postgresql.org/docs/current/jit-decision.html).
