# Диагностика запросов и сообщение о проблеме

Решение пользователя 26.10.2026: оценивать скорость всех запросов frontend/backend, находить узкие места и дать сотруднику кнопку отправки проблемы с последними действиями текущей сессии. Используется существующая система Pino/Sentry/TelemetryEvent, а не параллельный logger или отдельное хранилище тикетов.

Документ задаёт контракт реализации. Наличие исходников и тестов не подтверждает подключение всех запросов, реальное сохранение отчёта или выкладку. Отчёт приёмки должен различать выполненное и оставшееся покрытие.

## Общие ограничения

Сохраняется LOGGING_CONTRACT: глобальный ADMIN проверяется сервером при каждом просмотре; подробная диагностика 30 дней по серверному receivedAt. Обычные сотрудники отправляют только свою диагностику. Никаких passwords/cookies/tokens, содержимого заявок/сообщений/форм, имён файлов, поисковых строк, raw URL/query/hash, DOM text или записи экрана/ввода. Под «всеми» понимается охват технических попыток и значимых действий, а не сбор содержимого.

Каждая HTTP-попытка имеет отдельный requestId. Намерение пользователя связывает запросы через actionId/traceId; sessionId является отдельным диагностическим UUID, не ключом авторизации. Повтор запроса отличим от нового действия. Клиентские сведения остаются client_reported; совпадение с доверенным серверным событием устанавливается существующими правилами, не по одному присланному UUID.

## Реальное исходное покрытие

Node observation уже измеряет физический finish/close/aborted всех 95 API route templates и пишет Pino с безопасным шаблоном маршрута. Это не полное покрытие страниц/assets и не доказательство записи всех HTTP durations в БД/admin UI: существующий durable bridge имеет более узкий каталог. Фронтовые именованные действия и request-result частично подключены. Существующий ring ограничен 50 событиями, 5 минутами и 8 КиБ; его наличие не означает запись всех кликов.

## Первый исполнимый срез: сообщение о проблеме

Кнопка «Сообщить о проблеме» доступна в общей шапке/профиле. Диалог предлагает фиксированные причины: медленная работа (`slow`), неработающая кнопка/действие (`button`), ошибка (`error`), другая проблема (`other`). Показывается, что передаются технические действия/ошибки текущей сессии; свободный текст и введённые в других формах значения в первом срезе не собираются.

Один новый закрытый client event `client.problem.reported`, action `app.problem.report`: общие поля текущей schemaVersion 1/eventId/sessionId/actionId/seq/occurredAt/traceId; `errorId` используется как публичный номер отчёта, `reason` — фиксированный enum, `screen` — безопасный каталог экранов, `breadcrumbs` — неизменяемый очищенный snapshot. Добавление `home` в каталог экранов разрешено для Главной.

Shared contract определяет сериализованный breadcrumb на основе существующего валидатора: фиксированные kind/name, seq, UTC time, разрешённые числовые duration/status/attempt и закрытые outcome/state/errorCode. Неизвестные/вложенные поля, getter values и произвольные метки отклоняются; исходный объект не попадает в лог при отказе. Сервер повторно валидирует snapshot, а не доверяет клиентской очистке.

Snapshot содержит не более 50 последних событий за 5 минут; весь закодированный запрос, включая signed-session envelope, обязан уложиться в существующие 8192 байта клиентского batch и 16 КиБ collector. Старейшие события удаляются до достижения wire budget; UI сообщает фактическое количество. Не повышать лимиты молча и не считать oversized event успешно отправленным.

Сохранение идёт через существующий signed collector и TelemetryEvent без новой таблицы/миграции. Сервер привязывает событие к текущему проверенному actor и подписанной диагностической сессии. eventId стабилен при повторе; snapshot/намерение повторной отправки неизменяемы. Дедупликация не создаёт второй отчёт. После logout/смены actor/диагностической сессии старый snapshot и ожидающие отправки очищаются.

Сообщение «Отчёт отправлен» и копируемый номер показываются только после явного ACK accepted eventId от сервера. Enqueue, локальный UUID, отправленный fetch и вызов flush сами по себе не подтверждают сохранение. При disabled/unconfigured/offline/timeout/drop/rejection показывается честная ошибка с безопасным повтором; автоматические бесконечные повторы запрещены. Отчёт не задерживает бизнес-команды приложения.

Глобальный администратор на существующей странице диагностики видит anchor как сообщение пользователя, причину/экран/номер и упорядоченную безопасную цепочку; ссылки на серверные события соблюдают действующее same-actor/action/request правило. Нельзя выдавать пользовательский отчёт за подтверждённое серверное исключение.

## Полное покрытие измерений

В текущем срезе подключён пассивный PerformanceObserver для same-origin API fetch/XMLHttpRequest после готовности подписанной диагностической сессии. В каталог попадает только нормализованный шаблон из существующих API_ROUTE_TEMPLATES, duration и доступный браузеру status; query/hash/ID/исходный URL не сохраняются. Собственные collector/cleanup/admin-telemetry запросы исключены. До готовности identity запросы пропускаются; начавшиеся до смены actor/диагностической сессии не переносятся в новую. Неподдерживаемый observer, отсутствующие status/отменённые записи и кеш не подменяются выдуманными HTTP результатами. RSC/assets/external uploads/socket этим адаптером не покрываются. fetch не патчится, бизнес-команды не ожидают отправку диагностики.

Делегированный обработчик кликов пишет только закрытое имя известного действия или тип элемента (кнопка/ссылка/checkbox/select). Не читает textContent/aria-label/href/selector/ID/value и не регистрирует ввод текста. Поля с data-telemetry-private/contenteditable исключены. Карандаши темы/описания имеют имена task.title.edit/task.description.edit. Ring по-прежнему ограничен 50 событиями/5 минутами/8 КиБ; очередь доставки — 100 событий/64 КиБ с ограниченными попытками, поэтому это ограниченный диагностический контекст, не полная запись сессии.

Существующая ADMIN summary дополнена count/p50/p95/p99/max/slowCount (>=1000 мс), nearest-rank. client.observed и server.handler не смешиваются: клиентская запись — наблюдение, которое может пересекаться с другим адаптером той же попытки; серверный durable bridge всё ещё ограничен пятью маршрутами обработчиков. Полный физический HTTP для 95 API остаётся в Pino. В UI подписаны окно UTC, лимит/усечение и частичность сохранённой выборки; отсутствующие замеры не показываются нулями. Ручной snapshot не размножает latency observations или business failures.

Публичный номер ручного отчёта проверяется в транзакции на существующий anchor под advisory lock; повтор допускается только для того же неизменного actor/event. Конфликт даёт 409 без ложного accepted ACK. Поскольку остальные server writers не берут этот lock, это не глобальная гарантия уникальности: чтение отдельно отдаёт приоритет доверенной серверной ошибке и отвергает неоднозначные ручные anchors. После неудачной отправки сотрудник может повторить тот же отчёт либо явно начать новый; неизвестный результат старой попытки объясняется в UI.

Следующий общий срез расширяет существующий request adapter: frontend физическое время запроса, status/outcome/requestId, безопасный route template и связанное действие; backend physical HTTP duration отдельно от handler duration; там, где реально измерено, auth/ACL/DB/сериализация и очередь. Нельзя показывать отсутствующие stage durations нулями. Измеряются first render/navigation и click-to-visible-result отдельно от HTTP. Кеш-hit не объявляется сетевым запросом; отмена не является серверной ошибкой. Socket connect/join/reconnect/ACK, потеря событий и fallback имеют отдельные события.

В админке нужны count/p50/p95/p99/max, доли slow/error/cancel, разделение маршрута/метода/сборки/клиента/сервера/холодного и тёплого открытия. Всегда указывать размер выборки, полноту покрытия, усечение/потери очереди и окно UTC. Сравнение до/после возможно только на сопоставимых запросах. Контроллер телеметрии исключает собственную рекурсию; очередь/размер/время отправки ограничены. Увеличение объёма проверяется на нагрузку, чтобы диагностика не замедляла интерфейс и БД.

Не считать это расширение выполненным по одному каталогу. Нужен инвентарь call sites и фактические тесты для fetch/apiFetch, auth/session, uploads, RSC/navigation и socket; внешние секретные адреса не передаются. Политика сэмплирования отсутствует для заявленного полного покрытия; при потере/ограничении это явно показывается, не скрывается.

## Приёмка

Проверить schema/privacy adversarial cases, actor/session rotation, pending ACK/retry/idempotence, переполненный ring/wire size, off/503/offline/timeout, отсутствие рекурсивной телеметрии, ADMIN и отказ остальных ролей, границу 30 дней. Реальный отдельный QA сценарий: действия двух сотрудников → отчёт → подтверждённая запись в БД → администратор открывает тот же номер и видит только разрешённую цепочку. Native notification или тесты с моками не заменяют эту проверку. Production включение/конфигурация и фактическая очистка проверяются отдельно без вывода секретов.

Владение: root — интеграция/метрики запросов/выкладка; backend owner — shared event/schema/store/report DTO/tests; frontend owner — client snapshot/ACK lifecycle, кнопка/диалог/admin presentation/tests. До изменений общих файлов согласовать точный список и не править один файл одновременно.
