## Реализованная общая основа

- `src/lib/telemetry-sanitize.ts`: фиксированный allowlist полей с ограничениями типов/длины; вложенные произвольные данные отбрасываются целиком. UUID проверяются; секреты в message/cause/body/query не пересылаются. Источник строки `route` — явный шаблон от владельца API, не разбор URL. Sanitizer защищён от ошибочных getter/proxy; SDK событие при сбое очистки становится пустым.
- `src/lib/request-context.ts`: сервер создаёт новый UUID на HTTP-попытку; принимает только валидный `X-Action-Id`. Из контекста копируются только безопасные `actorId/route`; runtime extra-поля не могут подменить requestId. Общего изменяемого async/global request context нет.
- `src/lib/logger.ts`: Pino root/child вызовы и child bindings проходят общую очистку. Все свободные сообщения заменяются фиксированным текстом; для перечисленных точных legacy-сообщений socket/session заданы стабильные коды, остальные отмечаются `legacy.unclassified` и требуют миграции на именованные события. Sink/очистка не бросают в бизнес-путь; fallback с сырыми данными удалён.
- Pino сохраняет встроенный безопасный тип ошибки и извлечённые из V8 stack имена исходных JS/TS-файлов с номером строки/колонки; Sentry сохраняет такие координаты для `in_app` frames. Полный путь, source snippets, function/locals, cause и исходный message не сохраняются. Это сознательно уменьшает детализацию: совпадающие basename разных модулей могут требовать revision/source-map интеграции. Произвольные custom Error.name не принимаются.
- `src/lib/sentry.ts`: capture использует `withScope` с очищенным контекстом и явной scoped-identity, без общего `setContext`; ошибки SDK не заменяют бизнес-результат/исходное исключение. Совместимый legacy `setUser` оставляет только ID; новые server-request сценарии используют scoped контекст вместо глобального setter.
- Оба `sentry.*.config.ts` применяют общий sanitizer; автоматический tracing отключён, Replay integration удалена и обе replay rates равны нулю. Sentry инициализируется только при уже заданном DSN. Это не настраивает удалённые retention/access параметры аккаунта.
- `src/middleware/api-logger.ts`: опциональный явный контекст и второй аргумент handler; на возвращённый response записывается один фактический outcome (включая 4xx/5xx) и добавляется `X-Request-Id`; поддержаны immutable headers. Thrown value логируется безопасно и пробрасывается без изменения существующего API error DTO.
- Волна #37/#38 подключила общий wrapper к recurring POST/PATCH/process и диагностическому API, сохранив тип `Request` и явные шаблоны route. Фоновые отказы и события bridge/sender используют безопасные именованные события вместо сырых payload/error.message. В allowlist добавлен `recurringTaskId`: только внутренний идентификатор по тем же ограничениям, что taskId; тексты расписания, bearer и тело realtime в технические логи не попадают. ## Целевой контракт

### Локальный сквозной срез следующей волны

Волна 3 (`WAVE_3_RESULTS_2026-10-20.md`, локальный материал исходного рабочего пространства) реализовала закрытую клиентскую схему для одного `task.checklist.toggle`, bounded memory-очередь, same-origin action/operation propagation, signed analytics sessions, HMAC actor, collector, ADMIN read и bounded30-day cleanup. Серверные X-Error-Id обработанных4xx/5xx совпадают с итоговым техническим событием; X-Request-Id остаётся новым на попытку. Receipt/checklist/Activity коммитятся вместе по коду, authoritative projection имеет durable marker. Приватные поля в аналитический payload не копируются. Общая project policy используется с транзакционным клиентом вместо новой матрицы прав.

Это не завершение #54–#58: полный каталог, server-error storage/просмотр цепочки, ErrorBoundary, все HTTP/socket/job каналы, revision/release отчёты, health-метрики и UI #56 ещё требуют реализации. Реальные PostgreSQL/browser проверки и настройка scheduler/retention внешних sinks не выполнены. Schema migration подготовлена без применения; по умолчанию сбор выключен. Текущие технические Pino/Sentry фильтры продолжают действовать независимо от collector.

### Три назначения данных

1. **История бизнес-действий**: кто и когда выполнил разрешённое изменение заявки/прав. Источник истины — сервер после проверки прав, запись согласована с транзакцией изменения. История внутренних данных наследует их видимость; отображение через API, realtime, экспорт и уведомления фильтруется сервером. UI-телеметрия не доказывает совершение бизнес-действия.
2. **Техническая диагностика**: безопасные структурированные события об обработке операции, отказе, повторе и ошибке. Pino используется на Node.js-сервере; Sentry — дополнительный канал ошибок через единый адаптер. Клиент не импортирует серверный logger.
3. **Использование функций**: счётные UI-действия и результаты по фиксированному каталогу. Подробные события и диагностические цепочки доступны только глобальным администраторам и хранятся 30 дней. Право читать заявку или администрировать подразделение само по себе не даёт права читать диагностику сотрудников.

Одна операция может создать связанные записи разных назначений. У них разные правила видимости и хранения; нельзя подменять историю заявки сырыми логами или открывать подробную диагностику через карточку.

### Общая структура события версии 1

| Поле | Правило |
| --- | --- |
| `schemaVersion` | Число `1`. Несовместимое изменение повышает версию; consumer неизвестную версию отклоняет безопасно. |
| `eventId` | UUID экземпляра события. При повторной доставке сохраняется; collector не учитывает повтор повторно. Это не requestId и не ключ идемпотентности бизнес-команды. |
| `event` | Значение из закрытого каталога; `msg` — фиксированное человекочитаемое описание, без содержимого заявки. |
| `occurredAt`, `receivedAt` | UTC-время события у источника и приёма collector. receivedAt назначает сервер; клиентское время не используется для прав и сроков. Технический Pino `time` нормализуется адаптером, а не заменяет оба поля аналитического события. |
| `level`, `source`, `module` | Уровень; `client/server/socket/worker`; стабильное имя модуля. |
| `env`, `revision` | Среда и версия сборки, если известны. Отсутствующая revision не заменяется вымышленным commit. |
| `actionId` | Идентификатор одного пользовательского намерения; необязателен для автономного фонового запуска. |
| `sessionId` | Отдельный псевдонимный UUID аналитического контекста; меняется при logout/смене пользователя. Никогда не cookie, bearer, NextAuth session token или их значение. |
| `requestId` | Новый серверный идентификатор каждой HTTP-попытки. Для socket/job вместо него используется соответствующий `operationId`. |
| `traceId` | Опциональный идентификатор технической трассы: 32 hex-символа, без управляющих символов. Не доказывает личность и не включает автоматическую внешнюю отправку трасс. |
| `operationId`, `parentOperationId` | Для сообщения socket, фоновой задачи/дочерней операции; связь с вызвавшей операцией, если известна. |
| `outcome` | `success/rejected/conflict/failure/cancelled`; только там, где результат уже известен. |
| `actorId` | Внутренний ID из проверенной серверной сессии; до аутентификации отсутствует. Не брать actor/права из клиентской телеметрии. |
| `projectId`, `taskId`, `recurringTaskId` | Только известные серверу внутренние ID и только в разрешённом для назначения события контексте; текущий sanitizer допускает 1–128 символов `[a-zA-Z0-9_-]`. Не включать название/описание вместо ID. |
| `route`, `method`, `statusCode`, `durationMs` | Для HTTP: шаблон маршрута (`/api/tasks/:id`), метод, фактический статус, неотрицательная длительность. Query, hash и полный URL не включаются. |
| `errorId`, `errorCode` | Для сбоя: ID экземпляра ошибки и стабильный машинный код. Sentry event ID хранится отдельно как `sentryEventId`, если получен. |

Дополнительные поля задаются схемой конкретного события с allowlist и ограничениями длины/размера. Не передавать `Record<string, any>` из UI, запроса или исключения напрямую в sink. Неизвестные поля отбрасываются; невалидный payload отклоняется без записи исходного payload.

Реализованный закрытый каталог задаётся `src/lib/telemetry/contract.ts`, `catalog.ts` и `report-contract.ts`: checklist toggle, render failure и ограниченные HTTP-маршруты. Collector использует signed session, HMAC actor и серверный receivedAt. Это частичное покрытие приложения. Новые события добавляет владелец общей схемы вместе с валидацией, дедупликацией и тестами; агенты отдельных функций не расширяют payload произвольными полями.

Минимальный каталог: `ui.action`, `api.request.completed`, `api.request.failed`, `auth.result`, `socket.operation.completed`, `socket.operation.failed`, `job.completed`, `job.failed`. Предметные подтверждённые события добавляются владельцем общего каталога; статусы и права берутся из [согласованного lifecycle](../REQUEST_LIFECYCLE.md), а не из старого DnD-маршрута. Имя UI-действия фиксируется отдельно, например `request.clarification.respond`; значения полей формы и текст кнопки не становятся именем события.

### Корреляция и повторы

- UI создаёт `actionId` перед значимым действием и передаёт его в `X-Action-Id`. При сетевом повторе того же намерения `actionId` сохраняется; новая попытка получает новый `requestId` на сервере. Новый клик/новое намерение получает новый `actionId`.
- Сервер создаёт собственный `requestId` в начале обработки и возвращает `X-Request-Id` для успеха и обработанной ошибки. Клиентский `X-Request-Id` не принимается как серверный ID. `X-Action-Id` принимается только после проверки формата/длины; невалидный/слишком длинный ID отбрасывается без логирования сырого значения. Для версии 1 используются UUID; имена заголовков регистронезависимы.
- ID корреляции не являются правом доступа, ключом идемпотентности или доказательством личности. Серверные ключи идемпотентности и optimistic version проверяются отдельно. Повтор не создаёт вторую запись успешного бизнес-изменения; технические попытки остаются различимыми.
- Сервер привязывает проверенный actor к контексту конкретного запроса/операции. Параллельные запросы разных сотрудников не делят изменяемый глобальный context. Sentry scope/контекст изолируется на операцию, чтобы поля предыдущего пользователя не попадали в следующую ошибку.
- HTTP → сервис → БД → публикация realtime/job передают безопасный контекст явно либо через изолированный request context; нельзя терять ID при async-переходе. Фоновый запуск без UI имеет собственный `operationId`, а повтор запуска — новую попытку и стабильную связь с заданием.
- При серверной ошибке UI получает безопасный машинный код и `errorId` вместе с `requestId`; эти же значения связывают серверную запись и Sentry. Существующие DTO не меняются каждым агентом произвольно: адаптер ошибок и формат ответа интегрируются одним владельцем API. Клиентская ошибка без ответа имеет свой `errorId` и `actionId`; серверный requestId не выдумывается.

### Очистка данных

Allowlist применяется **до** Pino/Sentry/console/отправки по сети; redaction sink'а — дополнительный барьер. Единая безопасная сериализация используется и в fallback. Сбой logger не разрешает вывести сырой payload в console.

Не записываются: password/hash, session/cookie/Authorization, bearer/CSRF/reset/verification/access/refresh tokens, API keys, DSN с секретной частью, содержимое форм и клавиш, название/описание/комментарии заявки, внутренние сообщения, текст письма и subject, файлы/имена файлов/подписанные ссылки, сырой request/response body, полный URL/query/hash, SQL-параметры, email/ФИО. Для функций отправки почты достаточно типа шаблона, внутреннего ID операции и результата.

Проверка очистки покрывает произвольную вложенность разрешённых контейнеров, массивы, регистр ключей, URL-кодирование и повторяющиеся параметры. Ограничивается глубина, размер и длина; циклический объект/нестандартный thrown value обрабатывается безопасно. Неизвестный объект не сериализуется целиком «для отладки». Stack/message/cause исключения могут содержать секреты: в пользовательский ответ они не попадают, перед sink проходят общую очистку/ограничения; где надёжно очистить нельзя, остаются тип и безопасный код.

Технические события внутреннего обсуждения не содержат текста и метаданных файла. Просмотр истории/ошибки заново проверяет область доступа; клиентский фильтр и скрытая ссылка недостаточны. ID сущности также не возвращается неуполномоченному пользователю как способ подтвердить существование чужой заявки.

### Уровни, ошибки и надёжность

- `debug`: безопасные детали разработки; production по умолчанию `info`. `info`: успешное завершение и ожидаемый результат. `warn`: значимый отказ/конфликт/деградация; обычная отмена пользователем не превращается в исключение. `error`: неожиданный сбой операции; `fatal`: невозможность продолжить процесс.
- На HTTP-попытку одна итоговая запись с фактическим статусом, включая возвращённые handler'ом 4xx/5xx. Перехват только thrown exceptions недостаточен. Не записывать один exception повторно на каждом слое; владелец границы операции фиксирует его один раз и добавляет контекст.
- Потеря технической телеметрии не меняет успешный бизнес-результат; отправка ограничена по времени/размеру, очередь ограничена, сбой sink не вызывает рекурсивное логирование. Клиент не ждёт отправки аналитики перед выполнением действия.
- Для обязательной истории изменения/прав запись выполняется в транзакции с изменением; её ошибка не замалчивается best-effort helper'ом. Для внешних side effects используется согласованная надёжная доставка с защитой от дублей; эта записка не объявляет outbox реализованным.
- Sentry, Replay и иные внешние sinks в автоматических тестах подменяются stub; диагностические тесты не отправляют данные в настоящие аккаунты.

## Порядок внедрения и владение

1. Один владелец общего контракта реализует schema/catalog, sanitize, безопасную сериализацию ошибок и тип контекста. Утверждает имена событий и DTO; остальные агенты не создают собственные несовместимые helper'ы.
2. Один владелец API интегрирует контекст и error adapter на общих границах. Сначала представитель HTTP-success/4xx/5xx, затем socket/job/client. Правила прав и lifecycle не копируются в telemetry adapter.
3. #57 проверяет payload и очистку; #58 — фактическую цепочку UI → API → ошибка. После подтверждения на вертикальном сценарии остальные задачи подключают общий адаптер при изменении своего участка.
4. #56 потребляет только версионированный контракт с серверной проверкой роли глобального администратора и 30-дневной политикой подробных событий. Панель не получает прямой неограниченный доступ к логам и внутренним событиям.

Агент каждой продуктовой задачи добавляет безопасное событие своего значимого действия, проверку отказа и корреляции, а в отчёте указывает: событие/схема, точку записи, redaction, проверки и ограничения. Общие файлы logger/API/Sentry/schema меняет назначенный владелец интеграции; параллельные агенты согласуют нужное расширение.

## Приёмочная матрица #57–#58

| Проверка | Наблюдаемый результат |
| --- | --- |
| Schema, неизвестные поля/версии, лимиты, циклы | Безопасный отказ/отбрасывание без утечки исходных данных и без падения бизнес-операции. |
| Секреты в nested arrays, mixed-case keys, percent-encoded/repeated query, URL, message/stack/cause, console fallback | Секрет отсутствует во всех перехваченных sinks; разрешённые поля сохранены. |
| UI → успешный API, возвращённый 4xx/5xx, thrown exception, offline/timeout | Правильные outcome/status; request/action/error IDs совпадают там, где существуют; отсутствующий серверный ID явно отсутствует. |
| Повтор и параллельные запросы двух пользователей | Разные requestId; один actionId повторяемого намерения; нет смешения actor/context; бизнес-история не дублируется. |
| Чужая/внутренняя заявка, отзыв роли, поиск/экспорт/realtime | Нет утечки содержимого или диагностической цепочки; отказ не обходит серверные права. |
| Сбой Pino/Sentry/telemetry endpoint, очередь заполнена | Бизнес-результат сохранён, нет рекурсии/сырых console payload; отдельно проверяется rollback обязательной бизнес-истории. |
| Job/socket и повтор после сбоя | Сохраняется parent/operation связь; различимы попытки, нет повторного бизнес-события. |

Unit-тесты используют перехваченный sink, Sentry stub и фиксируемые ID/часы. Интеграционные проверки истории выполняются на отдельной тестовой БД с реальными транзакциями; E2E воспроизводит один управляемый сбой и проверяет UI ID против перехваченного безопасного события. Точные команды и результаты записываются по [регламенту](../TASK_WORKFLOW.md); наличие планов/старого отчёта не заменяет запуск.

## Принятые решения и оставшиеся границы

Сводка [#54–#58](../BACKLOG_CLARIFICATIONS_2026-10-20.md) предшествует текущему ответу пользователя. Теперь утверждено: подробные действия/ошибки доступны **только глобальным администраторам**, подробные события хранятся **30 дней**. Первая панель включает **оба раздела: ошибки и использование функций**. Сервер проверяет роль на каждом запросе просмотра/поиска/экспорта; администратор подразделения этого доступа не получает. Полная запись экрана/ввода не авторизована. Срок хранения обезличенных агрегатов отдельно не определён.

Реализация подробного хранилища должна удалять истёкшие события после 30 дней и исключать их из выдачи, даже если очередной cleanup ещё не запущен. Для collector отсчёт — от серверного receivedAt, срок — 30 × 24 часа; подмена occurredAt не продлевает хранение. Все sinks с подробными событиями, включая Sentry и резервные выгрузки, требуют согласованной фактической настройки срока; один фильтр интерфейса не обеспечивает удаление. Само наличие этого документа не доказывает внедрение очистки. Нужны проверки границы срока на фиксированных часах и фактической задачи удаления.

Контракт, очистка, корреляция и тесты на синтетических данных могут внедряться сейчас. Текущая настройка Replay должна быть приведена к отсутствию неавторизованной записи до эксплуатационного включения; этот документ не изменяет конфигурацию и не доказывает, что Replay сейчас фактически отправляет данные.

Срок 30 дней относится к подробной диагностике; он не означает автоматического удаления обязательной истории бизнес-действий. Физическое удаление истории и сроки обезличенных агрегатов отдельно не согласованы.

## Реализованный срез панели и ошибок, волна 4

Панель `/admin/telemetry` и все её API повторно проверяют текущего глобального ADMIN. Окно UTC `[from,to)` ограничено 30 сутками; независимо от выбранного окна чтение исключает receivedAt на границе retention и старше. Summary сканирует максимум10000 записей плюс sentinel; при усечении доля ошибок неизвестна. Агрегаты вычисляются на запрос, отдельного бессрочного хранилища агрегатов нет. Выключенный collector, неполная конфигурация, ошибка БД, отсутствие событий и недостаточная выборка различаются.

Использование: уникальные намерения actor/action, клиентские сессии actor/session и actor считаются только по `ui.action`; подтверждённые изменения — по server authoritative actor/operation. Серверная доля ошибок — уникальные server_observed actor/request со статусом5xx относительно всех наблюдаемых серверных запросов. Клиентские failure/cancel и render failure показаны отдельно. Покрытие не является оценкой продуктивности сотрудников или всей активности приложения. Retry/drop/collector latency не измеряются и не отображаются нулями.

Client render failure содержит только новый errorId, actionId, sessionId, seq, время и фиксированный RENDER_FAILURE. ErrorBoundary не показывает и не передаёт componentStack/message/raw context; Sentry вызывается через общий защищённый helper. Локальный код ошибки не обещает доставку. HTTP writer пишет безопасные финальные статусы только выбранных маршрутов с проверенным actor, best effort; collector/admin API не собирают аналитику о себе. eventId серверной записи генерируется независимо от доступного клиенту requestId. Потеря этой диагностики не меняет бизнес-ответ; гарантии durable business receipt на неё не распространяются.

Client UUID не подтверждает серверную ошибку. Для отметки server_verified клиентской цепочки требуется совпадение actorKey, requestId, actionId и errorId с доверенной серверной записью; прямой серверный anchor допустим без UI action. Breadcrumbs остаются client_reported, ограничены actor/session/seq и retention. Фильтры project/revision учитывают только события с записанными метаданными: client events и часть authoritative событий этих полей не имеют, поэтому нули при фильтрации не доказывают отсутствия использования. Revision берётся только из проверенного серверного commit SHA, а не из клиентского payload.

## Узкая граница предупреждений Next Server Actions, 23.10.2026

В Node `register()` устанавливает `installFrameworkWarningBoundary` перед загрузкой Sentry. Только одиночный `Error` с собственным data descriptor `__NEXT_ERROR_CODE` E788/E793 заменяется существующим Pino-событием `framework.server_action.rejected`: source=server, outcome=rejected, statusCode=404 и фиксированный errorCode. Текст ошибки, stack, cause и произвольный action ID не читаются и не передаются. Повторная установка не добавляет второй адаптер; сбой безопасного sink не вызывает сырой fallback. HTTP-ответ и диспетчеризация Server Actions не меняются.

Это ограниченная обработка двух диагностик установленного Next 15.5.28. Остальные предупреждения и console.error сохраняют прежнее поведение; документ не обещает очистку всех framework-логов. Проверка реального built HTTP после подключения обязательна отдельно от unit-тестов. Причина трёх production-событий 23.10.2026 не установлена этим изменением.

## API observation: Pino-first, интеграция #102

Node HTTP observer использует diagnostics_channel и закрытый каталог маршрутов: source path служит только для выбора статической метки, raw URL/query не сохраняются. Сервер создаёт UUID физической попытки и возвращает X-Request-Id; входной request/actor ID не подтверждает личность. Внутренний подписанный capability связывает Node request с wrapper и перезаписывается сервером; он не журналируется и не является правом доступа. Проверенный actor добавляет только существующий route/session механизм.

Физическое событие имеет durationKind=http и durationMs до finish/close/aborted; handlerDurationMs — отдельное необязательное измерение wrapper. Единственный finalizer очищает active context и исключает повтор на finish/close. Abort без отправленных headers не получает вымышленный HTTP status; частичный200 остаётся200 с outcome=aborted. Уже сформированные408/504 классифицируются timeout; observer не устанавливает таймаутов и не изменяет ответ, stream или обработку ошибки. Прямой/Edge wrapper fallback имеет durationKind=handler и не выдаётся за завершение физического HTTP.

Существующий best-effort DB bridge остаётся только у маршрутов своего каталога и с проверенным actor; его handler measurement не стало полной durable HTTP-историей. Наличие Pino observation не доказывает доставку в БД, доступность всех событий в admin UI, 30-дневное удаление, наблюдение ingress до Node или отсутствие raw framework/Nginx error logs. Установка через Next register ещё требует проверки холодного первого запроса: событие request.start до установки подписчика восстановить невозможно.
