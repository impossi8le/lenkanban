# Групповые и личные роли; импорт сотрудников

Решение владельца 28.10.2026 в текущем чате. Разрешены реализация, production-выкладка, импорт и релевантная проверка; результаты ниже не предполагаются выполненными.

## Продуктовый контракт

- Отдел определяет ответственный состав. Группы объединяют людей для массовых назначений. Роль — переиспользуемый профиль разрешений с областью (организация/отдел/доска). Личные назначения дополняют групповые по OR. Удаление из группы отнимает только права этой группы; личные права сохраняются. Источник прав виден администратору.
- Переиспользовать PrivilegeProfile и ScopedPrivilegeAssignment. Групповые назначения хранить отдельно в GroupPrivilegeAssignment с тем же scope CHECK. Не копировать групповые разрешения в личные строки.
- Добавить request.execute: действующий состав ответственного отдела (либо прежняя группа доски без отдела) AND подходящее явное разрешение AND текущая видимость/состояние обращения. Название профиля не даёт прав. Заблокированный пользователь не исполняет. Один исполнитель и существующие mutation/version/retry/Activity остаются обязательными.
- Сотрудник: обычная работа со своими/доступными обращениями по существующим правилам; роль не предоставляет чтение чужих обращений во всей организации. Исполнитель: request.execute, не заменяет отдел/видимость. Руководитель: использовать уже реализованную семантику управления отдела; если нужен отдельный permission request.manage, он не даёт global ADMIN и не отменяет запреты lifecycle. Новым людям руководителей сейчас НЕ назначать. Глобальные роли USER/ADMIN остаются отдельны.
- Персональный получатель и исполнитель различаются; не сокращать получателей обращений до пользователей с ролью Исполнитель.
- 391 импортируемая учётная запись, 52 группы. Русские короткие логины, три подтверждённых объединения, Мамаков отдельно — manifest work/people-import-20261028/plan.json. Все новые globalRole=USER. Пароль передаётся при исполнении защищённо; отсутствует в коде/аргументах/логах/CSV.
- Явно подтверждено владельцем: IT отдел - Техподдержка → отдел Поддержка + Исполнитель; ОКК и ОЗОК → Отдел качества + Исполнитель. Остальные группы → Сотрудник без права исполнения. Названия всех групп сохранить; не создавать 52 отдела/доски автоматически. Администраторы/Суперадмин из файла не означают ADMIN.
- Сохранить прежние аккаунты, пароли, globalRole, отделы, связи и право исполнения текущих действующих сотрудников. Дополнительные сохранительные scoped назначения допускаются только для подтверждённого текущего состава, не для всех пользователей организации.

## Исполнение и проверка

Один владелец schema/service/API DTO; один владелец общего resolver и resource/lifecycle integrations; один владелец admin UI; root владеет импортером/релизом/интеграцией/итоговой проверкой. До зависимой реализации согласовать имена DTO/permission/API.

Новые group grants проходят канонический profile decoder, активные group/member/profile и strict scope; серверы API/files/socket/notifications/search используют общий свежий resolver. Не кешировать роль в JWT. Мутации защищены от конкурентного отзыва через действующий совместимый lock order; topology lock после Project не брать.

Проверки: unit/route/component; реальная отдельная PostgreSQL (CHECK/FK/retry/conflict/revocation/импорт); браузерный вход и минимум два обычных пользователя; действующая/чужая область/без роли; открытый realtime и файлы после отзыва. Mocks не объявлять DB acceptance. Production: свежая encrypted off-VPS копия и восстановление отдельно, точная сохранность старых данных, схема только additive, без seed/reset/replay исторических migrations. Текущий image-only controller не использовать для DDL без адаптации.

На production применять только проверенный точный пакет, свежий dry-run, детерминированные IDs/operation receipts и точный manifest; повтор без дублей и без сброса паролей. Сначала blocked новые аккаунты, затем сверка/пилот/активация. При сбое — остановка новых доступов по manifest, без удаления истории и без слепого восстановления всей рабочей БД. Письма/сообщения автоматически не отправлять.

## Общее правило видимости и исполнители Безнала — уточнение владельца 28.10.2026

- Для всех досок обычный пользователь без действующего права исполнения именно этой доски видит только свои заявки и существующие явно предоставленные личные участия (автор, исполнитель/назначенный, наблюдатель). Само членство в отделе/группе, руководство, старый read-профиль или роль участника проекта не дают просмотра остальных заявок. Глобальный ADMIN и ограничения персональной аудитории/внутренних материалов остаются отдельными действующими правилами.
- Просмотр общих заявок требует той же актуальной eligibility, что исполнение: активный пользователь, соответствующий ответственный штат доски и явное scoped request.execute. Связанный отдел имеет приоритет; ответственная группа используется только при departmentId=null. Личные закрытые аудитории и DRAFT/deleted ограничения не обходятся этим правом.
- Владелец прямо подтвердил все три группы «Отдел продаж» (33), «Бухгалтерия» (7), «Операционисты» (5) исполнителями Безнала: 45 человек. На существующей доске без departmentId разрешены включение этих людей в её ответственную группу и board-scoped request.execute через три исходные группы. Их primaryDepartment и права других досок не менять; глобальных администраторов не назначать.
- Исполнитель доски может подать собственную заявку и затем сам взять её в работу и завершить по обычному маршруту. Пример владельца: Шамбулина Юлия, логин шамбулинаюлия. Авторство не запрещает self-claim при действующей eligibility; сотрудник без неё не может брать даже собственную заявку.
- Уточнение «остальные видят только свои» подтверждено отдельно. Проверять позитивные сценарии всех трёх групп, отрицательные другие группы/другие доски, собственную заявку обычного сотрудника, списки/поиск/историю/файлы/realtime и self-claim до завершения. Эти пункты — требования, а не утверждение о выполненной production-проверке.
