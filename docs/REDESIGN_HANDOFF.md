## Как открыть и что попробовать

Открыть `outputs/design/redesign-v1/index.html` двойным щелчком. Это один файл со встроенными CSS и JavaScript, без CDN, npm и обязательного подключения к Интернету. Ссылка на заказ открывает внешнюю CRM только по нажатию.

Для локального просмотра из корня проекта:

```powershell
python -m http.server 3857 --bind 127.0.0.1 --directory ./outputs/design/redesign-v1
```

Адрес просмотра — `http://127.0.0.1:3857/`. Этот сервер раздаёт только каталог прототипа.

Демонстрационный заявитель — Ольга Смирнова; исполнитель — Алексей Сидоров. Переключение справа вверху. «Клиент» в запросе пользователя означает сотрудника-заявителя; вход внешних клиентов не добавлен. Демоисполнитель обслуживает оба направления, чтобы можно было проверить оба интерфейса одним переключателем. Это не будущая модель выдачи прав.

Порядок знакомства:

1. В роли заявителя нажать одну из двух крупных карточек на Главной. Форма открывается сразу в нужный отдел.
2. Создать обращение. Оно попадает только в «Новые». В претензии доступны заказ, телефон и данные клиента.
3. Переключиться на исполнителя, открыть нужный отдел. Кнопка «Взять в работу →» появляется при наведении/фокусе на новой карточке; на сенсорном экране видна постоянно. Действие также доступно в открытой карточке.
4. Взять своё новое обращение: появляется имя исполнителя, обращение переходит в работу.
5. Запросить уточнение с комментарием. В роли заявителя найти обращение в «Ждут моего ответа». Обычный комментарий не снимает ожидание; «Ответить и вернуть в работу» снимает.
6. В роли назначенного исполнителя отметить решённым. Автор может переоткрыть с причиной. Закрытие исполнителем отдельно помещает обращение в архив.
7. Попробовать поиск, категории и фильтр срочности. У претензий фильтр называется «Повышенный риск».

Демоизменения сохраняются в `localStorage` с ключом `lenkanban-redesign-v1-demo`. Файловый и HTTP-просмотр могут иметь разные хранилища. «Начать пример заново» сбрасывает только демонстрационные данные после отдельного подтверждения в интерфейсе.

| Сценарий | Заявитель | Исполнитель |

## Предложения прототипа, ожидающие оценки пользователя

Следующие детали выбраны для работающего примера, а не объявлены новыми решениями пользователя:

- «Ждём сотрудника» показано как ожидание уточнения от автора. Проверить, согласен ли пользователь с этой трактовкой и заменой подписи «Ожидает ответа»/«На уточнении».
- «Решено» — завершение исполнителем; отдельное состояние «Закрыто» сохранено в архиве, чтобы не слить ранее согласованные состояния «Решена» и «Закрыта». Размещение закрытых в архиве требует оценки.
- Подписи двух уровней опасности в претензиях: «Обычная ситуация» и «Повышенный риск». Пользователь утвердил понятие, но не точные подписи.
- Для демонстрации номер заказа и телефон обязательны, имя необязательно. Обязательность полей пользователь отдельно не утверждал.
- Категории ИТ, формулировки подсказок, блок последних обращений, счётчики, архив и состав меню «Мои обращения» адаптированы из образцов и существующих сценариев. Проверить их на пользовательском просмотре.
- Категории не скрываются из-за раннего примечания пункта 8: новый HTML и последующее согласование формы претензий используются как ориентиры. Окончательный список категорий ИТ отдельно не утверждён.
- Список карточек сохраняет порядок демонстрационных данных; автоматическая сортировка по срочности/возрасту не добавлена без решения.

## Ограничения HTML

Это frontend-пример, а не тест безопасности или готовая замена Next.js:

- Нет сервера, SSO, реальной БД, реальных уведомлений, realtime, прав на уровне API, конкурентных запросов и гарантии идемпотентности.
- Нет загрузки файлов, черновиков, редактирования описания, управления наблюдателями, внутренних комментариев и реального удаления ошибочных обращений. При переносе редизайн не должен уничтожать уже согласованные функции.
- История/сообщения/всплывающие подтверждения в HTML — локальная имитация, не замена Pino/Sentry/Activity/существующих уведомлений приложения.
- Назначение выполняется сразу локально; в production обязательно сохранить серверные проверки, версию и защиту от двойного взятия.
- При переоткрытии демо предполагает доступность прежнего специалиста. В production проверяется актуальный состав группы; иначе возврат в очередь.
- Черновой макет адаптируется к узкому экрану; колонки прокручиваются горизонтально, текст не уменьшается ради четырёх колонок на телефоне.

## Последовательность реального внедрения после оценки

**Разрешение на переход уже дано.** Не создавать новый approval-gate и не заканчивать реализацию одним планом или HTML. Учитывать GLOBAL_CHANGES, в том числе пункты 16–17. Некритичные детали уточнять по ходу работы без остановки независимых задач; приоритет — фактическая реализация и проверенный продукт.

1. Получить замечания пользователя по HTML и обновить этот же прототип и GLOBAL_CHANGES. Отделить принятые решения от предложений выше.
2. Уточнить общий маршрут/подписи, два уровня риска, обязательность полей, правила старых приоритетов. Сначала обновить контракты.
3. Перенести тему, токены, меню и Главную, затем карточки и форму. Сохранить все реальные ограничения доступа и точки открытия карточки.
4. Подключить действия к существующему lifecycle-сервису. Удалить межколоночный DnD во всех активных реализациях. Проверить API/массовые пути, чтобы UI не стал единственной защитой.
5. Отдельно спроектировать хранение полей претензий/приоритета, совместимость и миграции. Никаких seed/reset/изменений рабочих данных без соответствующего объёма и разрешения.
6. Проверить состояния загрузки, ошибки сети, неизвестный результат, конфликт, потерю прав, пустые списки. В HTML они не имитируются полностью.
7. Пройти проверки по TESTING_CONTRACT: типы, целевой lint, затронутые component/unit, браузер desktop/mobile и роли. Реальная интеграция — только с явно разрешённой отдельной тестовой БД.

### Скорость при переносе

Сначала изучить существующие оптимизации приложения и снять baseline. Затем сравнить до/после в одинаковых условиях и объёме данных: холодная/повторная загрузка, переход Главная → отдел, открытие карточки/формы, ответ/назначение, фильтр/поиск, лента и счётчик уведомлений. Фиксировать сетевой waterfall, объём JS, длительные задачи/перерисовки и метрики загрузки/отклика браузера. Не подменять измерения основного приложения результатами автономного HTML.

Сохранить query-кэш, фоновые обновления и существующий socket/fallback. Новая страница уведомлений и колокольчик используют общие данные, а не два параллельных запроса/соединения без необходимости. Приоритетно устранить лишние перезагрузки, повторные fetch и тяжёлые синхронные операции; не маскировать медленную загрузку анимацией. Численные результаты, среду и непроверенные сценарии вынести в итоговый отчёт. Производительность ранее не измерялась набором `run-qa.cjs`, его зелёный статус доказывает только описанные функциональные проверки.
