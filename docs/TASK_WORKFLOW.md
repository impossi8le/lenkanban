# Правила работы с задачами

Источник задач — GitHub Issues репозитория `lenremont2/kanban_pochta`. Доска ведётся в нативном GitHub Projects. Канонический этап задачи хранится в поле **Status** карточки проекта. Каждая карточка соответствует issue, а issue хранит цель, ответственного, договорённости и доказательства результата.

При создании issue добавьте её в проект и выберите Status «Заведена». Шаблон issue сам по себе не добавляет задачу в проект и не устанавливает Status: проверьте это в разделе Projects у issue.

Перед реализацией применять [общую основу](engineering/README.md): единый контракт журналирования/корреляции, правила проверок и карту зависимостей. В плане задачи указывать, какой общий сервис прав, мутаций и событий используется; новая задача не вводит отдельную несовместимую реализацию. Общие требования закреплены в корневом [AGENTS.md](../AGENTS.md). Создание этих контрактов не завершает зависимые продуктовые задачи.

## Этапы и условия перехода

| Status в GitHub Projects | Что должно быть в issue |
| --- | --- |
| Заведена | Понятная цель, границы задачи и проверяемые критерии приёмки. Issue открыта. |
| В работе | Ответственный, комментарий о намерении, предполагаемые файлы и зависимости. Issue открыта. |
| На тестировании | Краткое описание фактических изменений, фактически изменённые файлы, ссылки на коммиты/PR и точные проверки с результатами. Issue открыта. |
| Завершена | Релевантные проверки и критерии приёмки успешно выполнены, доказательства опубликованы. После итогового комментария issue закрывается. |

Основной маршрут: **Заведена → В работе → На тестировании → Завершена**. Ответственный меняет поле Status в проекте или переносит карточку в соответствующую колонку доски, сгруппированной по Status. Блокировка обозначается отдельной меткой issue `status:blocked` и комментарием с причиной; это не пятый этап. Если у задачи остались прежние метки этапов `status:*`, они не определяют её этап: ориентируйтесь на Status в проекте.

## Как брать задачу

1. Прочитайте issue, критерии приёмки и связанные задачи. Уточните неоднозначности до зависящих от них изменений; независимую работу можно продолжать.
2. Назначьте одного ответственного в Assignees; если агент не имеет GitHub-аккаунта, укажите его имя в комментарии, а владельца сопровождения — в Assignees.
3. Опубликуйте комментарий о начале работы, перечислите намерение, предполагаемые файлы и зависимости. Установите Status «В работе» в проекте.
4. У каждого ответственного агента одновременно одна основная активная задача, включая этап тестирования. До переключения передайте или явно приостановите текущую задачу, зафиксировав состояние и следующий шаг. Блокировка не означает незаметного освобождения задачи.

Параллельные агенты работают с непересекающимся владением файлами или заранее согласованными участками. В issue фиксируются владелец каждого участка и точка интеграции. Изменение общих файлов сначала согласуется с их владельцем; чужие изменения не перезаписываются.

Предполагаемые файлы — план, а не отчёт о выполнении. При изменении границ работы обновите план и объясните причину. Короткие содержательные обновления нужны при смене подхода, обнаружении зависимости или риска, изменении объёма и передаче работы. Отчёт должен говорить, что выяснилось, что остаётся и какой следующий шаг.

## Проверка и завершение

Перед переходом в «На тестировании» опубликуйте фактический результат: поведение после изменения, список затронутых файлов, коммиты или PR и подходящие проверки. Для каждой проверки укажите точную команду или шаги ручной проверки, среду, ожидаемый результат и фактический результат. Различайте «запланировано», «выполнено успешно», «ошибка» и «не запускалось».

Если проверка ещё не запускалась, карточка остаётся на тестировании до появления результата. Если проверка обнаружила ошибку, верните Status в «В работе», опишите ошибку и следующий шаг. После исправления повторите затронутые проверки. Неприменимость проверки обоснуйте явно; это не то же самое, что невозможность её запустить.

Зависимость не отменяет независимые проверки: выполните всё доступное сейчас. При блокировке добавьте `status:blocked`, ссылку на блокирующую issue, точную причину, оставшиеся доступные проверки, владельца разблокировки и следующий шаг. Не меняйте основной этап, если сама работа не перешла на другой этап. Когда зависимость снята, удалите признак блокировки и выполните отложенные проверки.

Если нужная среда, данные, доступ или тест недоступны, зафиксируйте ограничение, непроверенные критерии и способ продолжения. Issue остаётся открытой; непроверенная работа не получает «Завершена». Не публикуйте секреты, токены, персональные данные или полные чувствительные логи.

Закрывайте issue только после успешных релевантных проверок и выполнения критериев приёмки. Итоговый комментарий должен позволять проверить это по коммитам, PR, результатам тестов или конкретным шагам приёмки. План, документ, назначение исполнителя или созданная карточка не доказывают выполнение продуктовой задачи. Для задачи, результатом которой является сам документ, проверяется именно согласованный документ и его критерии.

## Шаблоны комментариев

При начале работы:

```text
Беру в работу.
Ответственный: @пользователь / имя агента; сопровождение: @пользователь.
Намерение и ожидаемый результат: …
Предполагаемые файлы/участки и их владельцы: …
Зависимости: #… / нет. Следующий шаг: …
Проверки, которые планирую выполнить: …
```

При переходе на тестирование:

```text
Передаю на тестирование.
Фактически изменено: …
Фактически затронутые файлы: …
Коммиты/PR: …
Проверка: точная команда или шаги; среда; ожидаемый результат.
Результат: успешно / ошибка / не запускалось — факты и причина.
Критерии приёмки: выполнено …; осталось …
Ограничения и следующий шаг: …
```

При блокировке или ошибке:

```text
Блокировка / ошибка проверки: …
Связанная issue: #…
Основной этап: …; при ошибке проверки — «В работе».
Что удалось проверить независимо и с каким результатом: …
Что не проверено и почему: …
Ответственный за следующий шаг: …; действие для продолжения: …
```

При завершении:

```text
Завершено.
Результат по критериям приёмки: …
Коммиты/PR и фактически изменённые файлы: …
Успешные проверки: точные команды/шаги, среда и результаты.
Оставшиеся ограничения: нет / явно перечисленные ограничения вне критериев этой задачи.
Status в GitHub Projects установлен в «Завершена», issue закрывается.
```
