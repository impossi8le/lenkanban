# Навигация, устройство экранов и дизайн Ленканбан

Дата: 20.10.2026. Область: **корневое приложение `D:\Lenkanban`**. Вложенная `lenkanban/` не исследовалась. Это инвентаризация исходников, а не протокол визуальной приёмки: браузер, реальные роли, почта, файлы и серверные сценарии здесь не проверялись. Production-код не изменялся.

## 1. Как устроен продукт сейчас

Ленканбан — рабочее пространство проектов. Проект содержит настраиваемые колонки; задача находится в колонке, имеет название, описание, приоритет, срок, нескольких исполнителей, теги, чек-лист, вложения и обсуждение. Основная рабочая точка — `/projects/:id/board`. Доска, таблица и календарь являются тремя состояниями **одного экрана**, а не тремя существующими маршрутами. Карточка задачи открывается справа; прямой URL задачи поддерживается отдельно.

Входящие задачи, непрочитанные сообщения и уведомления — три разных сущности. `/inbox` показывает назначенные задачи с legacy-статусом `TODO`; `/messages` — задачи с непрочитанными сообщениями; колокольчик — системные уведомления. В приложении нет подтверждённого UI basemail, LDAP, подразделений, отдельного принятия передачи задачи, отчётов/чеков/лидов как самостоятельных бизнес-объектов. Они описаны как развитие в [почтовом backlog](../KANBAN_MAIL_BACKLOG.md) и [плане доступа](../ORG_ACCESS_MAIL_ROADMAP.md).

## 2. Полная карта страниц

В таблице перечислены все `page.tsx` корневого `src/app`, исключая HTTP API. `:id`, `:taskId` — идентификаторы записей.

| URL | Экран и вход | Действия и переходы |
| --- | --- | --- |
| `/sign-in` | Публичная форма email/пароля | Войти; «Забыли пароль?» → `/forgot-password`; регистрация → `/sign-up`. При необходимости доступна повторная отправка подтверждения email |
| `/sign-up` | Публичная регистрация, имя/email/пароль | Регистрация → состояние ожидания письма; «Войти» → `/sign-in` |
| `/verify-email?token=…` | Переход из письма | Проверка токена; успех → `/sign-in`; ошибка → вход либо повторная регистрация |
| `/forgot-password` | Запрос письма восстановления | Отправка email; возврат → `/sign-in` |
| `/reset-password?token=…` | Из письма восстановления | Новый пароль и повтор, минимум 8 символов; успех → `/sign-in`; без токена → ссылка `/forgot-password` |
| `/` | Главная после входа | Четыре показателя: проекты, активные, завершённые, просроченные; шесть недавно обновлённых доступных проектов. «Все проекты» → `/projects`; проект → его `/board`. Показатели сами по себе не являются фильтрующими ссылками |
| `/projects` | Список доступных проектов | Карточка → `/projects/:id/board`; «Новый проект» сразу создаёт «Новый проект» и открывает его; «Шаблоны» открывает панель шаблонов проектов |
| `/projects/:id/board` | Рабочий экран проекта | Переключатель доска/таблица/календарь; меню «Дополнительно»; создание, выбор и открытие задач; фильтры; панели настройки |
| `/projects/:id/tasks/:taskId` | Прямой адрес карточки | Общая `TaskDetailPanel`; закрытие в полном маршруте → `/projects/:id/board`. Переход с доски перехватывается parallel/intercepting route и показывает карточку поверх доски; закрытие модального варианта вызывает `router.back()` |
| `/my-tasks` | Все назначенные текущему пользователю задачи | Приоритет, срок, колонка, сортировка; карточка открывает локальную панель без смены URL; «В проект» → `/board?task=:taskId` |
| `/messages` | Непрочитанные сообщения, сгруппированные по проектам | Карточка с последним сообщением, автором, временем, счётчиком → `/board?task=:taskId`. Это не общий архив всех чатов |
| `/inbox` | Назначенные пользователю задачи `TODO` | Карточка → `/board?task=:taskId`; показывает приоритет, дату создания, дедлайн; отдельной команды «принять» нет |
| `/analytics` | Общая аналитика доступных данных | Сводные показатели, распределения по статусам/приоритетам, графики и нагрузка исполнителей; «Экспорт PDF». Переходов в отфильтрованный список из показателей не реализовано |
| `/settings` | Личный профиль | Email только чтение; изменение имени → PATCH профиля и обновление сессии; информация ID/глобальная роль. Нет вкладок безопасности, пароля, токенов или управления организацией |
| `/admin` | Только ADMIN | Redirect → `/admin/users` |
| `/admin/users` | Только ADMIN | Поиск по имени/email, очистка, таблица пользователей, смена `USER`/`ADMIN`, счётчики проектов/участий/токенов |
| `/admin/projects` | Только ADMIN, ввод URL вручную | Таблица проектов, владельцев, задач/участников; строки не ведут на доску; нет кнопки пагинации |
| `/debug-search` | Диагностика, отдельной ADMIN-проверки нет | Текст поиска и «Тест» вызывают API задач/проектов, выводятся сессия, доступные JS cookies и ответы; в обычном меню отсутствует |

Маршрутов `/projects/:id`, `/projects/:id/table`, `/projects/:id/calendar`, отдельной страницы уведомлений или глобальной страницы шаблонов в `src/app` нет. Это важно для проектирования ссылок и hotkeys.

## 4. Доска, виды и меню проекта

Переключатель «Доска / Таблица / Календарь» меняет локальный state; предпочтение хранится под общим ключом `kanban-view-preference` в localStorage, одинаковым для проектов и пользователей этого браузера. URL не фиксирует вид и фильтры. `?task=…` на `/board` преобразуется в канонический `/projects/:id/tasks/:taskId`.

### Доска

Колонки расположены горизонтально, каждая прокручивает свои карточки. Заголовок содержит название, цветовой маркер, количество и «+ Добавить задачу». В legacy-компоненте плюс открывает поле названия: Enter и blur создают задачу, Escape отменяет. Новая задача получает средний приоритет. Есть две реализации перемещения: legacy и V2, выбор — `project.dndV2Enabled`; не считать их поведение автоматически одинаковым. Доска имеет объявления перемещения для скринридера. V2 дополнительно содержит меню перемещения задачи; целевая колонка/позиция меняются без обязательного drag.

Карточка показывает название, приоритет, срок, исполнителей, теги и доступные счётчики сообщений/вложений/чек-листа. Открытие ведёт на адрес задачи. Для выбора нескольких задач предусмотрена массовая панель: изменить приоритет, переместить в колонку, применить, удалить, снять выделение. Однако путь выбора в доске сейчас не соединён с карточками — см. NAV-13. Добавление колонки доступно управляющим; быстрый путь сейчас использует два browser prompt: имя и HEX-цвет. Расширенное управление — через меню «Колонки».

`FilterBar`: колонка, приоритет (CRITICAL/URGENT/HIGH/MEDIUM/LOW), исполнитель (включая «Без исполнителя»), тег, «Сбросить». Исполнители/теги появляются при наличии соответствующих данных. UI тега выбирает один тег, хотя модель фильтра — массив. Сортировки: позиция; новые/старые; недавно/давно обновлённые; ближайший/дальний срок; высокий/низкий приоритет; название А–Я/Я–А. V2 разрешает reorder только при подходящем состоянии фильтров/сортировки (`isTaskReorderEnabled`); сценарий недоступного DnD требуется объяснять пользователю.

### Таблица

Собственные независимые фильтры `FilterBar`, поиск текста и сортировки заголовков. Столбцы: выбор, короткий ID, название, статус/имя колонки, приоритет, дедлайн. Строка открывает карточку. «Выбрать все» выбирает строки текущей страницы; массовые действия сразу меняют колонку/приоритет, «Отменить» снимает выделение. Меню массового приоритета таблицы пока содержит только четыре значения без CRITICAL. Экспорта выбранных задач в этом UI нет. Пагинация по 20: «Назад / Вперёд». Фильтры таблицы не синхронизированы с состоянием `ProjectBoardClient` для сохранённых представлений.

### Календарь

Показывает только задачи с дедлайном как события на дату/время дедлайна; цвет связан с приоритетом. Навигация «Назад / Вперёд / Сегодня» и виды «Месяц / Неделя / День / Список», «+ ещё». Событие открывает карточку. Нет создания задачи нажатием пустой даты и переноса срока drag-and-drop. Общие фильтры доски календарю не передаются.

Сначала требуется вручную перенести задачи; выбора назначения внутри удаления нет | `canManage` |
| Название проекта | Dialog с названием **и описанием**, отмена/сохранение; пустое имя и pending блокируют save | `canManage` |
| Сохранить как шаблон | Dialog: имя/описание, сохранить/отмена; пояснение о сохранении колонок и тегов проекта, без выбора включения задач | `canManage` |
| Повторяющиеся задачи | Sheet: создать правило; имя/описание, поля задачи, периодичность и дата старта; список, переключение активности, удаление. Работу расписания обеспечивает внешний вызов процессора, не открытая панель | Видно всем имеющим доступ |
| Автоматизация | Sheet: новое правило, имя/описание, событие, условия, действия; добавить/удалить условие/действие, создать/отмена; список, включить/выключить, удалить | Видно всем имеющим доступ |

События automation UI: создание задачи, смена статуса/приоритета, добавление исполнителя/тега, установка дедлайна. Условия: статус, приоритет, число исполнителей/тегов, наличие дедлайна, просроченность; операции сравнения/содержания/пустоты. Действия: уведомить исполнителей/создателя, добавить/удалить тег, изменить приоритет, назначить пользователя, переместить в колонку, добавить комментарий. Для назначения/колонки форма сейчас просит сырые ID (`AutomationRuleDialog.tsx:315`, `:327`), что требует знания технических идентификаторов.

Шаблоны проектов открываются также из `/projects`: использовать → диалог имени/описания нового проекта → создание и переход на его доску; есть удаление шаблона. Шаблоны задач и проектов — разные панели и API.

## 5. Карточка задачи и её внутренние действия

Общая панель `src/components/task/TaskDetailPanel.tsx`: фиксирована справа, до 980px, на узком экране вся ширина, затемнение фона, диалог с доступным именем. Верхняя строка: короткий ID, сохранить как шаблон, удалить, закрыть. В основной области название, приоритет, колонка, дедлайн с календарём/очисткой, исполнители, теги, описание, чек-лист и вложения. Отдельный блок содержит вкладки «Чат» и «История».

| Контрол | Работа и сохранение |
| --- | --- |
| Название | Обычный ввод сохраняется автоматически с индикаторами pending/saved/error и повтором; восстановленное название из черновика требует явного сохранения |
| Описание | Tiptap: жирный, курсив, маркированный/нумерованный списки, блок кода, цитата, undo/redo; явная кнопка «Сохранить», ошибка и повтор; несохранённый текст хранится локально |
| Приоритет / колонка / срок | Изменение отправляет обновление задачи; колонка учитывает optimistic version; срок выбирается/очищается |
| Исполнители / теги | Select/popover выбора, добавление/удаление связей; теги имеют цвет; несколько исполнителей поддерживаются |
| Чек-лист | Добавить, отметить выполненным, редактировать текст, сохранить/отменить, удалить; прогресс |
| Вложения | Выбор файлов и drop; изображения открывают lightbox; скачать/открыть/удалить. Наличие этих кнопок не подтверждает рабочую загрузку: см. NAV-01 |
| Чат | Загрузка истории/предыдущих сообщений, ввод, прикрепление файлов/вставка, отправка; индикация набора, повтор после ошибки, черновик; собственные сообщения можно редактировать/удалять, доступны реакции. Записи/редактирование/реакции используют Socket.IO; соединение и подтверждение сервера являются частью сценария |
| История | Лента действий задачи; не является отдельной страницей |
| Локальный черновик | Восстановить / удалить; предупреждение об ошибке browser storage. Черновик привязан к пользователю/задаче и браузеру, а не синхронизируется между устройствами |

## 6. Права и видимость

Факты по `src/lib/project-access.ts`, board page и admin layout:

| Роль/состояние | Чтение/запись проекта | Управление проектным UI |
| --- | --- | --- |
| Гость | Dashboard требует входа через middleware | Публичны пять auth-маршрутов |
| USER вне проекта | Нет доступа; helpers возвращают NotFound | Не должен видеть проектные данные |
| MEMBER | Читать и изменять задачи | Нет пунктов Колонки/Название/Сохранить проект как шаблон; участники доступны только для просмотра |
| PROJECT_ADMIN | Читать и изменять | `canManageMembers=true`, используется UI как `canManage`, включая колонки/название |
| Владелец | Полный проектный доступ | Управляющие пункты |
| Глобальный ADMIN | Полный доступ по helper, все проекты | Также `/admin/*`; для остальных admin layout отвечает notFound |

Здесь нет отдельной роли наблюдателя, read-only участника, подразделений, запрета просмотра части задач и отдельного разрешения на удаление задачи. Это не доказательство одинаковой авторизации всех API: фактический контракт каждого endpoint должен проверяться отдельно. Скрытая кнопка сама по себе не является защитой API.

## 7. Реализованный визуальный язык

Согласуется с [DESIGN_SYSTEM.md](../DESIGN_SYSTEM.md): спокойное плотное рабочее пространство, нейтральные поверхности, синий акцент, цвет приоритета дополнен подписью. ## 9. Целевой дизайн для развития — предложения, не реализованный факт

1. **Один контракт рабочего экрана.** Хранить вид/фильтры/сортировку в URL или другом явно согласованном состоянии; использовать его в кнопках, палитре, hotkeys и сохранённых представлениях. Команда «Новая задача» должна знать проект и колонку, а вне проекта предложить проект.
2. **Общая модель навигации desktop/mobile.** Один список разделов и admin-раздел с подразделами; одинаковые active/aria-current и счётчики. Контекст проекта показывать постоянно, добавить возврат из карточки и понятную цепочку «Проекты → Проект → Задача».
3. **Развести термины.** Назвать Inbox «Новые назначенные задачи» либо переопределить по бизнес-процессу; назвать Messages «Непрочитанные обсуждения», если архив не планируется. Уведомления должны иметь согласованный журнал и рабочие actionUrl.
4. **Один контракт сохранения.** Название — auto-save; описание — явно save; обоим нужны dirty/pending/saved/error и восстановление черновика. Подтверждение сервера показывать отдельно от состояния socket. Закрытие с несохранённым текстом должно иметь согласованное поведение.
5. **Проектные настройки как единый диалог с вкладками.** «Общие», «Колонки», «Участники», «Шаблоны», «Автоматизация», «Повторения» — возможная структура, которую следует проверить с пользователями. Нынешнее «Название проекта» переименовать в «Настройки проекта», поскольку там есть описание. Числовые ID в automation заменить выбором сущностей.
6. **Расширение ролей по требованиям.** Отдельно проектировать чтение, создание, редактирование, удаление, управление участниками и автоматизациями; LDAP/подразделения/ограниченная видимость остаются задачами backend и UX, а не косметической настройкой sidebar.
7. **Стабильная плотность и доступность.** Общие semantic tokens, достаточная зона нажатия, текстовые названия команд, клавиатурная альтернатива всем открытиям/перемещениям; не кодировать состояние только цветом. Графики дополнить доступной таблицей/текстом, проверить контраст динамических тегов, 320px и 200–400% zoom.

## 10. Приёмочный маршрут и связь с существующей wiki

Этот документ дополняет [архитектуру](../wiki/architecture.md), [каталог](../wiki/catalog.md), [дизайн-систему](../DESIGN_SYSTEM.md) и исторические [UI](../UI_AUDIT_2026-09-14.md)/[accessibility](../ACCESSIBILITY_AUDIT.md) аудиты. Наличие компонентов и старых passing-отчётов не означает прохождение текущих пользовательских сценариев. В отличие от архитектурной сводки здесь разделены фактические маршруты, локальные состояния и несоединённые команды.

Минимальная будущая приёмка: гость → регистрация/подтверждение/вход/восстановление; MEMBER/PROJECT_ADMIN/ADMIN → видимость меню и прямые URL; проект → создать задачу → все scalar-поля/исполнители/теги/чек-лист/вложения → refresh; доска ↔ таблица ↔ календарь всеми тремя способами; сохранённое представление в каждом виде; открытие задачи из поиска, Inbox, Messages, direct URL; закрытие/back/reload; сообщение в двух сессиях, разрыв сети и восстановление; шаблоны/повторения/automation с реальным результатом; >50 admin-записей; desktop/320px/light/dark/system; клавиатура, focus, screen reader, reduced motion. Для каждого шага фиксировать роль, ожидаемый результат, фактический URL, screenshot при необходимости и запись после reload. До этой проверки документ остаётся evidence-based картой исходников, а не актом сдачи продукта.
