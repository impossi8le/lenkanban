## UX-01 · P2 · Соединить выделение карточек с массовыми действиями доски

**Факт по коду.** `src/components/kanban/Board.tsx:106` хранит `selectedTaskIds`; `:667` определяет toggle; `:950`–`:951` передаёт selection и callback в legacy-column; `:983`–`:984` подключает `BulkActionsBar`. Но `src/components/kanban/Column.tsx:23` только объявляет callback в props, `:26` не извлекает его, а карточке в `:157` передаёт лишь `isSelected`. В `src/components/kanban/Card.tsx:388` компонент `KanbanCard` получает задачу и признак выделения, без команды изменения. `src/features/kanban/dnd/KanbanDndBoard.tsx:37`–`:54` также не задаёт контракт выбора/selection callback. Это статически несоединённый путь взаимодействия, а не утверждение о выполненном browser-тесте.

**Предлагаемый объём.** Явный выбор карточек и согласованный selection state в legacy и V2; использование уже существующей массовой панели. Не смешивать с #36: там порядок/сортировка, здесь выбор объектов для действия.

**Критерии приёмки:**

- [ ] В legacy и V2 есть доступный checkbox/эквивалент с названием задачи, состоянием checked и достаточно большой зоной нажатия.
- [ ] Две карточки можно выбрать и снять выбор мышью и клавиатурой; счётчик панели равен количеству ID, повторный выбор не создаёт дубликат.
- [ ] Выбор не открывает карточку и не начинает drag; открытие карточки и DnD остаются самостоятельными действиями.
- [ ] Массовая смена колонки/приоритета затрагивает только выбранные задачи; после подтверждения результат сохраняется после reload. Удаление подтверждается и затрагивает только выбранные задачи.
- [ ] Смена проекта, удаление задачи и фильтрация не оставляют незаметного опасного выделения: согласовать сброс либо явное отображение скрытых выбранных задач.
- [ ] Pending исключает повторную операцию; ошибка сохраняет понятный выбор и возможность повторить; «Снять выделение» доступно с клавиатуры.
- [ ] Проверка параметризована по legacy/V2 и не ограничивается тестом передачи callback: проверить пользовательский выбор → вызов API с правильными IDs → отображение результата.

- [ ] Из таблицы и Моих задач название открывается через Tab+Enter; при использовании кнопки Space также работает; checkbox и «В проект» не вызывают второе открытие.
- [ ] После закрытия карточки focus возвращается на инициатор, при удалении — на логичное существующее действие; Escape закрывает только верхний уровень.

- [ ] Проверены 200% zoom, клавиатура и хотя бы один screen reader; axe/DOM-проверки дополняют ручную приёмку, а не заменяют её. Снимки/результаты фиксируются отдельно, без декларации прохождения до запуска.

## UX-03 · P2 · Унифицировать приоритеты и текст Inbox

**Факт по коду.** `src/app/(dashboard)/my-tasks/page.tsx:83` задаёт четыре записи `priorityConfig`; `:398` использует MEDIUM для неизвестного значения, включая поддерживаемый CRITICAL. В `:212` comparator имеет четыре приоритета и для CRITICAL получает undefined. При этом CRITICAL присутствует в фильтре `:317`. `src/app/(dashboard)/inbox/page.tsx:93`–`:101` отображает CRITICAL через fallback «Низкий». `src/components/views/BulkActionsToolbar.tsx:25`–`:30` перечисляет четыре приоритета; это расходится с одиночным редактированием и bulk-панелью доски.

Inbox запрашивает только `assignedToMe=true&status=TODO` (`src/app/(dashboard)/inbox/page.tsx:28`), но его пустое состояние говорит «Все задачи выполнены» (`:59`). `useQuery` извлекает только `data`/`isLoading` (`:26`); отдельной ветки `isError` нет, поэтому ошибка с default `[]` может выглядеть как отсутствие задач. Это статический риск ложного пустого успеха, а не зафиксированная ошибка live API.

**Граница с #36.** Не дублировать issue о rank, V2 и legacy sorting. В UX-03 унифицировать **названия/семантические стили, MyTasks comparator и опции UI**. Согласованный порядок CRITICAL → URGENT → HIGH → MEDIUM → LOW использовать общий с решением #36.

**Критерии приёмки:**

- [ ] CRITICAL явно отображается как «Критический» в Моих задачах, Inbox и всех используемых шаблонах/меню, без fallback к среднему/низкому; стиль соответствует токенам приоритетов обеих тем.
- [ ] Все пять значений доступны в допустимых одиночных и массовых действиях, включая таблицу. Существующие значения проходят round-trip без изменения.
- [ ] Сортировка Моих задач ставит CRITICAL выше URGENT; поведение неизвестного значения определено и не выдаёт NaN/ложное известное имя.
- [ ] Назначенная IN_PROGRESS при отсутствии TODO даёт «Нет новых задач» с пояснением области списка; UI не сообщает, что вся работа выполнена.
- [ ] Ошибка API показывает отдельную ошибку и действие повторного запроса; во время загрузки показывается loading; успешный пустой результат отличается от обоих состояний.
- [ ] В тексте Inbox явно отражено, что выбран TODO/новые задачи; если нужен иной бизнес-смысл «входящих», его согласовать до замены фильтра, не менять его молча.

## UX-04 · P2 · Добавить cursor-пагинацию администраторских списков

**Покрытая часть NAV-09.** Desktop/mobile-вход, переходы Users/Projects и доступность раздела уже относятся к [#42](https://github.com/lenremont2/kanban_pochta/issues/42). Не заводить повторную задачу на sidebar.

**Оставшийся факт по коду.** `src/app/(dashboard)/admin/users/page.tsx:40` объявляет `nextCursor`, запрос в `:52` всегда задаёт `take=50` и не передаёт cursor. `src/app/(dashboard)/admin/projects/page.tsx:27` также объявляет `nextCursor`, `:33` запрашивает только `?take=50`. Оба экрана отрисовывают `items`, но не используют nextCursor и не имеют перехода к следующей порции. Backend уже поддерживает cursor: users `src/app/api/admin/users/route.ts:18`, `:44`–`:46`, `:65`–`:67`; projects `src/app/api/admin/projects/route.ts:17`, `:32`–`:34`, `:52`–`:54`. Ограничение касается UI-доступа к результатам >50; выборка такого объёма live здесь не выполнялась.

**Критерии приёмки:**

- [ ] На фикстуре ≥51 пользователь и ≥51 проект каждая запись достижима через UI; запросы используют возвращённый cursor, не подбирают ID на клиенте.
- [ ] Определён один UX: страницы с историей cursors либо «Загрузить ещё». При `nextCursor=null` продолжение скрыто/disabled; pending исключает дубли запросов.
- [ ] При неизменном dataset между порциями нет пропусков и дубликатов; сортировка соответствует серверному `(createdAt desc, id desc)`.
- [ ] Смена/очистка поиска пользователей сбрасывает cursor и набор страниц; cache key включает search/cursor; после смены роли данные и выбранная страница обновляются согласованно.
- [ ] Ошибка следующей порции сохраняет уже загруженные строки, сообщает ошибку и позволяет повторить. Empty показывается только для успешной пустой первой выборки.
- [ ] Кнопки имеют понятные имена, loading объявляется screen reader; после подгрузки focus не теряется. Проверены desktop и узкая ширина.
- [ ] Не-ADMIN по-прежнему не получает список через прямой URL/API. В #42 отдельно добавить переход на доску из названия проекта, если он входит в согласованный сценарий администрирования.
