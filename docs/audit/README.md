## Как работает продукт

Пользователь регистрируется, подтверждает email и входит. В проекте владелец/участники работают с задачами, колонками, исполнителями, тегами, сроками, чек-листом и обсуждениями. Один проект имеет доску, таблицу и календарь. Личные списки, сообщения, входящие и аналитика собирают доступные пользователю данные. Администратор имеет отдельные страницы пользователей и проектов. Подробные права и исключения описаны в архитектуре; скрытие пункта меню не является проверкой доступа.

Next.js обслуживает UI и API; PostgreSQL/Prisma хранит данные; отдельный Socket.IO-процесс доставляет события. Перемещение V2 использует rank, версию задачи и operationId для конкурентных изменений. Шаблоны, повторения и автоматизации существуют, но имеют описанные в backlog разрывы. Вложения требуют отсутствующего upload backend. Требования LDAP, подразделений и почтовых процессов пока не равны реализованной модели.

## Результат проверки

- API smoke: 30 успешных проверок ожиданий; из них три специально подтверждают дефекты HTTP 404. Регистрация, сессия, создание проекта/задачи, редактирование, checklist/chat, move/retry/conflict и повторное чтение проверены в отдельном синтетическом проекте.
- Командные проверки: typecheck FAIL; Vitest не исполнил ни одного тестового тела; lint корневого `src` — 74 ошибки/55 предупреждений, полный каталог — 149/113.
- Расчёты monthly/weekly исполнены изолированно: обнаружены пропуск февраля и игнорирование недельного интервала. Остальные findings имеют указанный уровень доказательств.
- Карта интерфейса сверена по исходникам. Живой UI проверен частично. Матрица ролей, browser DnD, reconnect, mobile/a11y, cron, полное удаление/массовые операции и production остаются предметом последующей приёмки.

Успешная проверка ожидания ошибки не означает работающую функцию. HTTP 200 страницы не доказывает гидратацию или работоспособность её кнопок. Существование теста не доказывает его прохождение. См. индивидуальные ограничения в документах.

## Как использовать в следующей задаче

1. Найти сценарий в навигации и соответствующую issue в backlog; проверить актуальный Status в GitHub Projects.
2. По архитектурной карте найти все пути записи: обычное редактирование, move, bulk, шаблоны, recurring, automation. Изменение одного handler может не охватить остальные.
3. Взять задачу по [регламенту](../TASK_WORKFLOW.md), зафиксировать владельца файлов и проверяемый результат.
4. Выполнить релевантные проверки из плана. Обновить этот аудит при изменении поведения; историю старых результатов не переписывать.

Исходники приложения находятся локально и пока не опубликованы в целевом репозитории. Указатели `src/...:строка` и `prisma/...` относятся к этому снимку. Документация и логи не включают `.env`, пароли, cookies, токены и почту. GitHub публикация аудита содержит документы и evidence, а не исходники приложения.
