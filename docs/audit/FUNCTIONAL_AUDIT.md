## Подтвержденные недочеты и заготовки issues

### F-01 · P1 · В DnD V2 сортировка не передается в список карточек

Источник: `src/components/kanban/Board.tsx:315`, `:897`; `src/features/kanban/dnd/KanbanDndBoard.tsx:212`.

`filteredTasks` сортируется, но V2 получает только `visibleTaskIds` как Set и нормализованный snapshot исходных `tasks`. V2 берет `controller.state.taskIdsByColumn`, применяет только фильтрацию через Set и сохраняет канонический порядок. Значение `sortBy`/порядок `filteredTasks` в V2 не передается.

Воспроизведение: включить DnD V2; создать две карточки, у которых порядок позиций отличается от порядка названий/дат; выбрать «По названию (А-Я)» или «Новые первыми». Ожидается выбранный порядок, реализация продолжает использовать порядок snapshot. Это вывод по коду; живой UI в рамках данного раздела не проверен.

Критерии приемки: все варианты сортировки меняют визуальный порядок в V2; сортировка не перезаписывает сохраненные rank; возврат «По позиции» восстанавливает канонический порядок; режим DnD корректен при активной сортировке.

### F-02 · P2 · CRITICAL сортируется ниже LOW в legacy-доске

Источник: `src/components/kanban/Board.tsx:237`, `:276`, `:282`; допустимое значение подтверждено `src/lib/validators.ts:4`.

В `priorityOrder` нет CRITICAL, поэтому fallback равен 0. Чистое исполнение comparator дало `URGENT, HIGH, MEDIUM, LOW, CRITICAL` для «Приоритет (высокий)».

Воспроизведение: в legacy-режиме поместить в одну колонку задачи CRITICAL и LOW, выбрать сортировку по высокому приоритету. Критическая окажется после LOW; при сортировке по низкому приоритету — перед LOW.

Критерии приемки: порядок по убыванию `CRITICAL > URGENT > HIGH > MEDIUM > LOW`; возрастающий порядок обратный; поведение проверено для всех допустимых значений.

### F-03 · P1 · Канонический endpoint перемещения не запускает status_changed автоматизации

Источник: `src/app/api/tasks/[id]/move/route.ts:110`, `:122`; сравнение: `src/app/api/tasks/[id]/route.ts:255`.

После `moveTask` endpoint вызывает только `emitTaskMoved` и возвращает результат. В endpoint и каноническом move-service нет вызова `processAutomationRules`. Между тем PATCH задачи явно вызывает `status_changed`. Статус при каноническом перемещении действительно меняется согласно workflow колонки.

Воспроизведение: создать правило «Статус изменен → добавить комментарий», переместить задачу между колонками с разными workflow через `/api/tasks/{id}/move`. Статус изменится, но правило по этому пути вызвано не будет. Вывод подтвержден анализом call path, без live исполнения автоматизации.

Критерии приемки: каноническое успешное изменение workflow вызывает правило; same-column reorder и перемещение без изменения статуса не вызывают его; повтор `operationId` не создает повторных side effects; rollback не вызывает автоматизацию.

### F-04 · P1 · Ежемесячное расписание пропускает короткий месяц

Источник: `src/app/api/recurring-tasks/route.ts:208`; `src/app/api/recurring-tasks/process/route.ts:266`; третья копия для обновления — `src/app/api/recurring-tasks/[id]/route.ts:270`.

`setMonth` вызывается до установки дня. У 31 января перевод месяца переполняется в март, после чего clamp работает уже по марту. Изолированное исполнение двух функций (create и process): `2027-01-31 12:00`, monthly, interval=1, dayOfMonth=31 → **2027-03-31**, ожидается 2027-02-28. В третьей функции update обнаружен тот же порядок операций чтением кода; отдельно она не исполнялась.

Критерии приемки: 31 января → 28/29 февраля → 31 марта; проверены дни 29/30/31, високосный год, interval>1; создание, обновление и обработка используют одинаковые правила.

### F-05 · P1 · Еженедельный интервал игнорируется при выборе дней недели

Источник: `src/app/api/recurring-tasks/route.ts:180`; `src/app/api/recurring-tasks/process/route.ts:240`; третья копия для обновления — `src/app/api/recurring-tasks/[id]/route.ts:244` (добавление дней `:262`); UI явно обещает «Каждые N недель» в `src/components/recurring/RecurringTaskDialog.tsx:258`.

В ветке непустого `daysOfWeek` вычисляется ближайший день в пределах недели, `interval` не используется. Изолированное исполнение двух функций (create и process): понедельник `2027-01-04`, interval=2, daysOfWeek=[1] → **2027-01-11**, ожидается 2027-01-18. Третья реализация update содержит тот же пропуск interval по результатам чтения; отдельно не исполнялась. Issue #37 должен охватить все три пути.

Критерии приемки: interval=1/2/3 соблюдается для одного и нескольких дней недели; неделя привязана к определенному якорю; начальное и последующие срабатывания следуют одному контракту.

### F-06 · P1 · Обработчик повторов открыт без CRON_SECRET

Источник: `src/app/api/recurring-tasks/process/route.ts:21`; `src/middleware.ts` исключает `/api/*` из matcher.

Проверка авторизации выполняется только при truthy `CRON_SECRET`; session/API user не проверяются. Без переменной любой HTTP POST проходит к чтению расписаний и созданию задач по всем проектам. Внешняя доступность зависит от сетевой конфигурации; deployment в рамках этого раздела не проверялся и запрос, создающий задачи, не выполнялся.

Критерии приемки: отсутствие серверного секрета запрещает обработку с контролируемым ответом; неверный/отсутствующий bearer запрещен; только валидный секрет разрешает обработку; тест проверяет отсутствие любых записей при отказе.

### F-07 · P1 · Создание повтора и продвижение расписания не атомарны

Источник: `src/app/api/recurring-tasks/process/route.ts:66`, `:152`, `:161`.

В транзакцию входит только создание Task. Чеклист, теги, исполнители и `recurringTask.update(nextRunAt)` выполняются после commit отдельно. Сбой между созданием и обновлением расписания оставляет созданную задачу и старый due nextRunAt; следующая обработка создаст дубль. Два обработчика также читают один due список до транзакций без атомарного захвата расписания. Это подтвержденный структурой сценарий отказа; конкуренция/сбой на живой БД не инъецировались.

Критерии приемки: сбой любого шага не оставляет частичной задачи; один occurrence создает ровно одну задачу при одновременных cron вызовах и retry; продвижение расписания и создание связей атомарны либо защищены уникальным occurrence/idempotency ключом.

### F-08 · P1 · Проверки качества не исполняют тесты из-за отсутствующего peer dependency

Источник: `src/test/setup.ts:1`; `package.json`, `vitest.config.ts:9`.

Общий setup загружает jest-dom для всех проектов, включая Node. Пакет `@testing-library/dom` отсутствует. Итог `npm test`: 150 failed files, `Tests no tests`; typecheck также не видит re-export API React Testing Library.

Критерии приемки: после установки dependencies из lockfile `npm test` исполняет тестовые тела; typecheck корректно разрешает Testing Library; отдельно представлены root unit/component результаты и безопасно пропущенные DB integration. Количество обнаруженных файлов не выдавать за количество исполненных тестов.

### F-09 · P2 · Корневые globs включают вложенный дубликат приложения

Источник: `tsconfig.json` include `**/*.ts`, `**/*.tsx` и exclude только `node_modules`; `vitest.config.ts` include/exclude; `eslint.config.mjs` ignores.

Typecheck содержит ошибки из `lenkanban/src/`; Vitest собирает корень и дубль, а exclude `e2e/**` не защищает `lenkanban/e2e/**`. Общий lint дает 149 ошибок против 74 в отдельно проверенном корневом `src/`. Это искажает результат и затрудняет определение, какую версию реально проверяли.

Критерии приемки: корневые команды проверяют только выбранное приложение и не подбирают вложенные e2e; если дубль нужен — имеет отдельную явную команду; документация объясняет источник истины. После исправления повторить typecheck/test/lint и обновить фактические результаты.
