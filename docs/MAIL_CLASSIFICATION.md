# Локальная классификация собранной почты

Реализован первый вариант для задач [#23](https://github.com/lenremont2/kanban_pochta/issues/23) и [#24](https://github.com/lenremont2/kanban_pochta/issues/24): правила классификации и воспроизводимый отчёт. Это не выполненный разбор всего архива. Данные получает отдельный [сборщик](MAIL_COLLECTOR.md); пока сборщик не подтвердил полный охват, отчёт остаётся частичным либо непроверенным. Нормализация рабочих эпизодов #22 и экспертная проверка правил ещё нужны перед импортом задач.

## Запуск

Нужен Node.js 24; классификатор использует только стандартную библиотеку, не требует Docker и не отправляет почту во внешние сервисы.

```powershell
node scripts/mail/classify-mail.mjs --input .mail-work/run
node scripts/mail/classify-mail.mjs --input .mail-work/run --output .mail-work/run/report
node --test tests/mail/classifier.test.mjs
```

Выход: `report/report.json` для машинной обработки и `report/report.md` для просмотра. Код завершения: `0` — охват объявлен полным и проверки не выявили расхождений; `2` — partial/unverified; `1` — ошибка входных данных/записи. Код 0 не является независимым доказательством полноты источника или точности категорий. Ошибки не печатают исходный текст письма. При ошибке предыдущий успешно записанный отчёт может остаться в папке — проверяйте код завершения.

## Контракт данных

`messages.ndjson` обязателен: по одному объекту на строке, UTF-8. Поля: `source_instance`, `source_message_id`, `topic_id`, `source_url`, `title`, `body_text`, `sent_at`, `author_text`, `attachments`, `content_status`. Непустые source_instance и source_message_id обязательны: отсутствие идентификаторов останавливает обработку, чтобы не объединять разные письма.

`topics.ndjson` содержит обнаруженные темы с topic_id/source_url и необязательным source_instance. При одном источнике source_instance наследуется от сообщений. Несколько источников нужно явно различать в метаданных. `manifest.json` передаёт scope, snapshot_at, coverage_status, discovered_unique_topics, collected_unique_messages, failed_topics, unfinished_pages и errors. При отсутствии manifest охват unverified; topics необязателен, отсутствие метаданных не доказывает, что все темы собраны.

Идентичность сообщения — пара source_instance + source_message_id. Одинаковый текст при разных IDs сохраняется. Точная повторная строка по содержательным полям учитывается один раз; collected_at и различие ссылки страницы не создают новую версию. Разные содержательные версии одного ID карантинируются: один элемент unmatched с причиной conflicting_duplicate, количество вариантов и общий охват unverified. Для анализа правок нужен будущий механизм версий, а не незаметная перезапись. Позиционные IDs сборщика ненадёжны при изменении пагинации и требуют проверки.

## Категории и смысл результатов

Начальная таксономия основана на проверенной выборке 40 тем (сырая выборка не публикуется: содержит рабочие идентификаторы): отчёты; претензии/качество; отправка чеков клиентам; сменные передачи; телемаркетинг → продажи; благодарности; подключение партнёров; бухгалтерские документы; клиентский клуб; обращения о мошенниках; отказ от автообзвона; корпоративная запись; дежурства; календарные объявления; зарплатные уведомления.

Правила видны в `scripts/mail/classifier-core.mjs`. Заголовок даёт более сильный сигнал, чем отдельное упоминание в тексте. Единственный сильный кандидат получает основную категорию. Слабый сигнал, отсутствие подходящего правила и равные сильные кандидаты остаются unmatched с причиной и дополнительными метками. ЧЕКИ не считаются расходами: категория receipts требует одновременно упоминания чека, клиента и отправки/получения. Одно слово «чеки» недостаточно. Неполное содержание и позиционные IDs требуют ручной проверки даже при уверенном заголовке.

confidence — уровень подтверждения правилом, **не вероятность и не измеренная точность**. Приведённый текст сообщения может содержать цитаты и несколько процессов: правила не умеют надёжно отделять их. Сообщение не равно самостоятельной задаче: выделение эпизодов внутри длинных тем и связь одной заявки с несколькими письмами остаются задачей #22. Автоматического объединения по тексту/номеру заявки нет.

Каждое уникальное собранное сообщение получает ровно одну основную категорию или unmatched. Контрольный баланс:

```text
collected_unique_messages = classified_messages + unmatched_messages
```

В отчёте отдельно подсчитываются темы и сообщения. Темы разных групп могут пересекаться, если их сообщения классифицированы по-разному. Обнаруженные темы без сообщений вынесены отдельно: они не входят в unmatched. Неизученные страницы и недоступная почта также не входят в unmatched. Заявленный complete понижается до partial при ошибках/незавершённых страницах; расхождение счётчика сообщений с manifest или конфликт IDs даёт unverified.

Каждая группа содержит предложение типа инструмента, поля карточки и статусы. Отчёты, чеки, продажи, смены и отказы от обзвона — кандидаты досок; дни рождения и дежурства — кандидаты календаря; клуб — реестра; финансовые и чувствительные обращения требуют отдельной проверки доступа. Предложения не создают реальные доски, задачи и изменения в почте.

## Хранение и проверки

Вывод по умолчанию не включает body_text, author_text и вложения. Он сохраняет заголовки, идентификаторы и ссылки; в заголовках могут быть имена и другие персональные данные. Храните исходники, профиль браузера и отчёты локально в исключённом из Git каталоге `.mail-work`, ограничьте доступ средствами ОС. Не публикуйте реальные отчёты вместе с кодом. Markdown экранирует HTML/табличную разметку; ссылки допускаются только HTTP(S) без встроенного логина/пароля. Отчёт всё равно содержит внешние ссылки — открывайте только знакомый источник.

Тесты используют синтетические письма: отправка чеков и отличие от расходов, слабые/конфликтующие сигналы, дедупликация по ID и конфликт версий, баланс частичного охвата, независимость от порядка, отсутствие тел/авторов в выводе, экранирование Markdown и работа CLI. Проверка на реальном корпусе с ручной разметкой ещё не выполнена; полнота архива и качество правил пока не доказаны.
