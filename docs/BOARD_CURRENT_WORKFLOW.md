# Как сотрудники взаимодействуют на доске сейчас

Снимок корневого приложения `D:/Lenkanban`, проверен чтением исходников 20.10.2026. Это доска приложения, а не GitHub Projects для разработки.
Документ описывает **наличие и правила кода**; новые продуктовые, браузерные и сетевые проверки в этой работе не запускались. Состояние рабочей БД и сервера не подтверждено.
Номера строк относятся к локальным исходникам на момент чтения; исходники приложения могут ещё отсутствовать в опубликованном Git-репозитории.
Новый согласованный процесс описан отдельно в [REQUEST_LIFECYCLE.md](REQUEST_LIFECYCLE.md); он не считается уже реализованным.

## Короткий путь сотрудника

1. Сотрудник получает членство в проекте либо является его владельцем.
2. Открывает проект и видит доступные задачи проекта, а не только созданные или назначенные ему.
3. Создаёт задачу прямо в выбранной колонке; отдельной отправки из личного черновика серверный маршрут не требует.
4. Участники проекта редактируют задачу, назначают одного или нескольких исполнителей, меняют колонку и обсуждают её в чате.
5. Колонка определяет статус; завершение и возврат происходят обычным изменением колонки, без отдельной роли заявителя или приёмки.
6. События пытаются обновить открытые клиенты; персональные уведомления создаются для предусмотренных конкретным вызовом получателей.

Это общая совместная доска участников проекта. Наличие `createdById` и исполнителей сейчас не создаёт согласованные новые роли «автор / ответственная группа / наблюдатель».
Основание: `prisma/schema.prisma:180`, `src/lib/project-access.ts:12`, `src/app/api/tasks/route.ts:191`.

## Кто имеет доступ

| Участник | Чтение и изменение по текущему общему HTTP-предикату | Управление участниками в общем helper |
| --- | --- | --- |
| Посторонний обычный пользователь | Нет | Нет |
| MEMBER проекта | Да, в пределах всего проекта | Нет |
| PROJECT_ADMIN | Да | Да |
| Владелец проекта | Да | Да |
| Глобальный ADMIN | Да, helper разрешает без проверки членства | Да |

Доказательство: `src/lib/project-access.ts:14`, `:40`, `:49`, `:54`, `:64`, `:70`, `:76`.
Роли хранятся в `prisma/schema.prisma:10`, `:15`, `:160`; членство уникально по паре проект/пользователь (`:175`).
Таблица описывает общий helper: конкретные endpoints дополнительно имеют собственные проверки, которые нужно сверять при изменении доступа.

Список задач ограничивается владельцем/членством проекта; глобальный ADMIN имеет исключение. `assignedToMe=true` добавляет добровольный фильтр исполнителя.
Он не является серверной политикой «сотрудник видит только своё»: без фильтра доступны остальные задачи проекта.
Основание: `src/app/api/tasks/route.ts:42`, `:56`; одиночное чтение проверяет проект в `src/app/api/tasks/[id]/route.ts:51`.

## Создание и поля

Быстрое создание на доске отправляет `title`, `columnId`, `projectId` в `/api/tasks`; после успеха оптимистическая карточка заменяется серверной.
Основание: `src/components/kanban/Board.tsx:596`, `:638`.
POST проверяет авторизацию и доступ к проекту, выбранную колонку либо берёт первую по порядку; сразу создаёт Task и фиксирует автора.
Статус выводится из `workflowKey` колонки, приоритет по умолчанию MEDIUM. Затем вызываются событие создания и правила `task_created`.
Основание: `src/app/api/tasks/route.ts:181`, `:191`, `:205`, `:236`, `:273`, `:276`.

Существующий `TaskForm` содержит название/описание и состояние приоритета, статуса, срока; валидатор допускает эти дополнительные параметры.
Это наличие компонента/контракта, не подтверждение, что все поля корректно проходят каждый UI-путь: POST сейчас явно записывает название, описание, колонку, статус, приоритет и автора; `deadline` в его `data` не передаётся.
Основание: `src/components/task/TaskForm.tsx:39`, `:50`, `:59`; `src/lib/validators.ts:11`; `src/app/api/tasks/route.ts:236`.
Отдельного поля/режима личного черновика, отправки группе и SLA-паузы в модели Task нет (`prisma/schema.prisma:180`).

## Кто редактирует и назначает

PATCH задачи разрешён глобальному ADMIN, владельцу или любому участнику проекта; не проверяет, является ли пользователь автором или исполнителем.
Допускаются название, описание, приоритет, срок, позиция, колонка и параметры контроля перемещения. Отдельного ограничения автора после отправки здесь нет.
Основание: `src/app/api/tasks/[id]/route.ts:95`; `src/lib/validators.ts:21`.

PUT `/tasks/:id/assignees` также доступен любому участнику проекта, владельцу и ADMIN. Он принимает массив `userIds`, а не одного исполнителя.
Назначаемые лица должны быть участниками или владельцем проекта; массив заменяет текущие назначения. Членство только в чужом подразделении не является отдельным основанием доступа.
Основание: `src/app/api/tasks/[id]/assignees/route.ts:20`, `:50`, `:65`, `:92`, `:104`.
Схема допускает несколько исполнителей: уникальна пара задача/пользователь, а не одна строка на задачу (`prisma/schema.prisma:285`, `:293`).

## Статусы, выполнение и удаление

Колонки динамические; у каждой есть `workflowKey`. Совместимый статус хранится в Task, но колонка — основа перемещения.
Прямой PATCH одного `status` отклоняется с `STATUS_REQUIRES_COLUMN`; изменение выполняется через выбор колонки.
Основание: `prisma/schema.prisma:140`, `:184`, `:191`; `src/app/api/tasks/[id]/route.ts:74`.
POST `/tasks/:id/move` требует проектного права записи, а не назначения исполнителем. Сервис проверяет принадлежность колонки тому же проекту и версию задачи.
Он выводит статус из целевой колонки, пишет перемещение в историю и меняет revision; отдельной бизнес-матрицы автор/исполнитель для переходов в этих местах нет.
Основание: `src/app/api/tasks/[id]/move/route.ts:108`; `src/features/kanban/server/move-task-service.ts:219`, `:228`, `:293`, `:300`.

В стандартном валидаторе перечислены TODO, IN_PROGRESS, IN_REVIEW, DONE; `REVIEW` колонки преобразуется в IN_REVIEW.
Это не согласованный новый маршрут «Черновик → На рассмотрении → В работе ↔ На уточнении»: переименование колонок само по себе не добавит его ограничения и таймеры.
Основание: `src/lib/validators.ts:3`; `src/features/kanban/server/move-contract.ts:40`.
Удаление задачи разрешено по тому же признаку ADMIN/владелец/участник и вызывает `prisma.task.delete`, без проверки автора, стадии или отдельного сценария ошибочной доски.
Основание: `src/app/api/tasks/[id]/route.ts:337`, `:351`. Это физическое удаление записи, а не утверждённая новая политика хранения.

## Обсуждение и вложения

Старый `/comments` возвращает 410 и направляет к `/messages` (`src/app/api/tasks/[id]/comments/route.ts:3`).
HTTP GET/POST сообщений проверяет доступ к проекту и читает/создаёт ChatMessage. Поля внутреннего/обычного комментария в схеме ChatMessage нет.
Основание: `src/app/api/tasks/[id]/messages/route.ts:54`, `:122`, `:136`; `prisma/schema.prisma:242`.
HTTP POST в прочитанном handler только сохраняет сообщение и возвращает ответ; вызова уведомлений или broadcast там нет (`messages/route.ts:136`).

Socket `message:send` отдельно проверяет членство/владение, сохраняет сообщение, рассылает его в комнаты задачи и проекта, затем вызывает уведомление исполнителям.
Автор своего сообщения может редактировать и удалять его при сохранённом доступе к проекту; это не новая согласованная политика неизменности сообщений.
Основание: `src/socket/server.ts:264`, `:340`, `:365`, `:372`, `:403`, `:409`, `:453`, `:459`.

Task хранит массив метаданных вложений JSON. PATCH вложений заменяет этот массив после проверки общего проектного доступа; персональной видимости файлов этот handler не задаёт.
Основание: `prisma/schema.prisma:196`; `src/app/api/tasks/[id]/attachments/route.ts:45`, `:65`.
UI отправляет файлы в `/api/uploads/direct` и удаляет метаданные через PATCH; наличие этих кнопок не доказывает работающую загрузку/защищённое скачивание.
Основание: `src/components/task/TaskAttachments.tsx:42`, `:59`, `:84`. При чтении 20.10.2026 файлы `src/app/api/uploads/direct/route.ts` и `uploads/presign/route.ts` отсутствовали; внешний upload-сервис не проверен.

## Уведомления и обмен между открытыми клиентами

| Вызванный обработчик | Получатели по прочитанному коду |
| --- | --- |
| Назначение | Новые исполнители, кроме назначившего самого себя |
| Смена статуса через PATCH | Исполнители задачи, кроме изменившего статус |
| Новое сообщение через socket | Исполнители задачи, кроме автора сообщения |
| Приближение срока | Исполнители; наличие функции не доказывает запуск планировщика |

Основание: `src/lib/notification-triggers.ts:7`, `:17`, `:39`, `:71`, `:129`, `:207`, `:231`; вызовы назначения — `src/app/api/tasks/[id]/assignees/route.ts:163`, смены статуса — `src/app/api/tasks/[id]/route.ts:242`.
В прочитанном move-handler после перемещения есть только emit, без того же вызова уведомлений/автоматизаций (`src/app/api/tasks/[id]/move/route.ts:110`, `:122`).
Уведомление — запись Notification в БД, затем попытка Socket.IO emit; автоматическая доставка email этим кодом не подтверждается.
Основание: `prisma/schema.prisma:313`; `src/lib/notifications.ts:25`, `:41`.
Наблюдатели и иерархия руководства не участвуют в этих выборках получателей. Согласованная новая рассылка автору/наблюдателям/руководству* требует доработки.

События доски уходят в комнату всего проекта через HTTP-мост с таймаутом; ошибки журналируются, запись задачи от сбоя доставки не откатывается.
Socket join проверяет владельца/членство, без HTTP-исключения для глобального ADMIN — предикаты сейчас расходятся.
Основание: `src/socket/board-events.ts:8`, `:31`, `:54`; `src/socket/server.ts:46`, `:191`, `:211`.
Персональные уведомления пытаются использовать `getSocketIO()` локального процесса, тогда как события доски используют HTTP-мост; работа доставки между процессами требует отдельной проверки (`src/lib/notifications.ts:25`).

## История и границы подтверждения

PATCH уже записывает значимые изменения названия, описания, приоритета и срока; назначения/снятия также пишутся в транзакции.
Основание: `src/app/api/tasks/[id]/route.ts:122`, `:194`; `src/app/api/tasks/[id]/assignees/route.ts:114`; перемещения — `move-task-service.ts:300`.
API истории разрешает проектное чтение либо ADMIN и отдаёт последние 50 записей (`src/app/api/activities/route.ts:17`, `:30`, `:34`, `:47`).
Activity удаляется каскадно с задачей и автором действия; это не неизменяемый административный аудит (`prisma/schema.prisma:298`). Полнота истории всех путей создания, файлов и автоматизаций не установлена.

В этой сверке подтверждены исходники, а не успешная работа всего сценария. Runtime-проверки нескольких пользователей, upload/download, доставки уведомлений и отзыва открытых соединений остаются отдельной приёмкой.
Главные изменения целевого процесса: управляемый круг заявителей и независимые ответственные группы; личная подача; один исполнитель; видимость по ролям; уточнение с паузой; обычные/внутренние комментарии и новая рассылка.
Для реализации использовать [спецификацию](REQUEST_LIFECYCLE.md) и [карту задач](REQUEST_LIFECYCLE_BACKLOG.md), не переносить автоматически текущие широкие проектные права в новую модель.
