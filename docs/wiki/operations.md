# Эксплуатация

Сверено с локальными исходниками 20.10.2026. Этот документ описывает конфигурацию и порядок проверки выпуска. Доступ к удалённому серверу, его uptime, активная сборка, reverse proxy и резервные копии при этой сверке не проверялись.

## Топология по файлам

`server.js` поднимает HTTP-сервер Next.js с портом из `PORT` (по умолчанию 3555). `npm start` запускает именно этот файл. При `NODE_ENV`, отличном от `production`, он включает dev-режим Next.js; для выпуска среду нужно задать явно и предварительно выполнить сборку.

Socket.IO находится в `src/socket/server.ts` и запускается отдельно на `SOCKET_PORT` (по умолчанию 3556). Сам HTTP-сервер Socket.IO не запускает. Строка лога `server.js` с WebSocket URL порта HTTP не является доказательством наличия Socket.IO на том же порту.

В `ecosystem.config.js` описаны PM2-процессы `kanban-v2` и `kanban-v2-socket`, один fork-процесс каждого типа, автоперезапуск, порты 3555/3556 и абсолютный серверный каталог. Это конфигурация исторического окружения, а не подтверждение существующей инфраструктуры; локально запускать её без адаптации нельзя. Конфигурации Nginx и systemd в корневом снимке не представлены, поэтому маршрутизацию внешнего HTTPS нужно проверять на целевом окружении отдельно.

## Согласованность окружения

| Настройка | Что проверить |
| --- | --- |
| `DATABASE_URL` | Оба процесса используют нужную БД; значения не попадают в журналы/документацию |
| `NEXTAUTH_URL`, `NEXTAUTH_SECRET` | Правильный origin и стабильный секрет авторизации |
| `APP_URL`, `EMAIL_FROM`, `SMTP_*` | Адреса ссылок и проверенный почтовый транспорт |
| `NEXT_PUBLIC_APP_URL` | CORS origin Socket.IO; сервер читает эту переменную напрямую |
| `NEXT_PUBLIC_SOCKET_URL` | URL клиента, доступный через reverse proxy; публичные переменные учитываются при сборке |
| `SOCKET_PORT` | Отдельный Socket.IO и HTTP-мост событий используют одинаковый порт |
| `NODE_ENV`, `PORT` | Режим production и HTTP-порт |

Socket.IO проверяет пользовательскую сессию через жёстко заданный `localhost:3555`; изменение HTTP-порта требует учесть эту зависимость. Его CORS имеет исторический внешний origin по умолчанию, поэтому нельзя полагаться на fallback в новой среде.

PM2-конфигурация явно передаёт только часть переменных. В частности, `NEXT_PUBLIC_APP_URL` и `NEXT_PUBLIC_SOCKET_URL` не перечислены в её `env`-блоках: проверьте итоговое окружение запуска и сборки, а не только наличие строк в `.env`. `ecosystem.config.js` вызывает `require('dotenv')`, хотя `dotenv` не объявлен прямой зависимостью `package.json`; наличие транзитивного пакета не следует считать устойчивым контрактом установки.

`httpServer.listen(PORT)` Socket.IO не ограничивает интерфейс loopback. Обработчик `POST /internal/emit` принимает внутренние события без проверки учётных данных; ограничьте его доступ доверенным локальным вызовом и не публикуйте этот путь через proxy. CORS сам по себе не защищает HTTP-мост. Реальная внешняя доступность из локального кода не установлена.

В SMTP-транспорте `src/lib/email.ts` установлено `tls.rejectUnauthorized: false`. Перед внешним выпуском требуется отдельное решение по проверке сертификатов и тест отправки/подтверждения писем. Успех регистрации не подтверждает доставку письма: API сохраняет пользователя даже при SMTP-ошибке.

## Подготовка выпуска

1. Определите точный набор исходников, параметры сборки и версию схемы. В текущей копии `.git` отсутствует: старый хэш из отчёта нельзя использовать как локально проверенный HEAD.
2. Выполните проверки по [development.md](development.md), зафиксировав ошибки и пропуски. `next build` не включает ESLint в текущей конфигурации.
3. Для изменения схемы подготовьте план миграции и проверенную резервную копию. `db:push` из локальной установки и особенно `db:reset` не являются процедурой обновления рабочей базы.
4. Соберите в отдельном каталоге, сохранив совместимую пару старых исходников и сборки. `generateBuildId` в `next.config.mjs` формирует `build-<timestamp>`; сам ID не доказывает успешный выпуск.
5. Проверьте итоговое окружение, reverse proxy, HTTP, Socket.IO и закрытость внутреннего моста. Согласуйте конкретный выпуск согласно процедуре целевой среды.
6. Переключите подготовленную сборку и перезапустите затронутые процессы. Проверьте вход, сохранение после перезагрузки, real-time между двумя сессиями и почту.
7. При отказе верните совместимую пару исходников/сборки. Откат данных и схемы — отдельная операция, не автоматическое следствие отката файлов.

Это контрольный список для подготовки, а не готовый deploy-скрипт. Исторические временные команды нельзя повторять без проверки путей, прав и текущего состояния. Наличие API обработки повторяющихся задач не подтверждает, что на сервере настроен планировщик.

## Резервирование и наблюдаемость

Сохраняйте БД, данные вложений при наличии внешнего хранилища, защищённую конфигурацию, исходники и совместимую сборку. Проверяйте восстановление в изолированном окружении. Периодичность резервирования и срок хранения не заданы локальной документацией как подтверждённая работающая политика.

`.next/cache` и вся `.next` имеют разное назначение: очистка кэша не должна уничтожать сборки для отката. Перед очисткой измеряйте размер, проверяйте абсолютные пути и сохранность нужных артефактов.

В исходниках есть Pino и конфигурации Sentry; это не подтверждает поступление событий в сервис мониторинга. Для проверки состояния фиксируйте HTTP-ответы, журналы процессов и конкретный функциональный сценарий без записи секретов и пользовательских данных.
