# Почта и предупреждение Chrome

Сверка кода: 20.10.2026. Live-проверки Search Console, TLS и VPS в этот день не выполнялись. Сведения ниже о 13.10.2026 — историческая запись; нового подтверждения закрытия инцидента в репозитории нет.

## Инцидент 13.10.2026 — закрытие не подтверждено

На скриншоте пользователя красная страница Chrome «Опасный сайт» с пояснением о фишинге и Google Safe Browsing. Это репутационная блокировка, а не типичная страница ошибки TLS. Она не доказывает сама по себе ни взлом, ни ложное срабатывание.

В записи от 13.10.2026 указаны проверки без отключения валидации TLS:

- `HEAD https://kanban.lenremontn8n.ru/sign-in` → 200.
- TLS-handshake с проверкой имени и доверия прошёл.
- Сертификат: `CN=kanban.lenremontn8n.ru`, issuer Let's Encrypt YE2; срок 11.09.2026–10.12.2026.
- Серверный и локальный HEAD совпадают: `c89cac6`; это ограниченная сверка, не антивирусный аудит.

Точная причина классификации и её охват (URL, поддомен или более широкая область) пока неизвестны. Публичный Transparency Report не удалось получить через инструмент просмотра. Нельзя объявлять сайт безопасным на основании HTTP 200 или действительного сертификата.

Google подтвердил владение через HTML-файл `public/googled314bd337d4cf2fd.html`. Файл размещён также на VPS; его нельзя удалять при следующем выпуске, пока этот способ подтверждения используется.

После размещения перезапущен только PM2-процесс `kanban-v2`, чтобы Next.js обнаружил новый public-файл. Файл и `/sign-in` вернули HTTP 200. База данных, DNS, сертификат и socket-процесс не изменялись.

В отчёте «Проблемы безопасности» показана одна категория: **«Обманные страницы»**. В поле «URL страниц с проблемами» — **«Отсутствует»**. Следовательно, категория теперь подтверждена непосредственно Search Console, но конкретная причина и поражённые страницы всё ещё неизвестны. По состоянию записи 13.10.2026 запрос на пересмотр не был отправлен и снятие блокировки не было подтверждено; состояние на 20.10.2026 неизвестно.

## Что требуется для закрытия

### Проверка тестового письма 13.10.2026

По ссылке, предоставленной пользователем для теста, встроенный браузер показал «Email успешно подтвержден» и затем автоматически перешёл на `/sign-in`. Красное предупреждение в этом браузере не появилось. Токен и адрес тестовой почты в документацию не включены. Подтверждение изменило состояние тестовой учётной записи; повторное открытие одноразовой ссылки не воспроизводит исходный сценарий.

Это подтверждает работоспособность данного перехода и подтверждения почты в этой сессии, но не снятие блокировки Google Safe Browsing в обычном Chrome. Полный сценарий регистрации самостоятельно не проверялся: письмо передал пользователь. `artifacts/search-console-2026-10-13/verification-redirect.png` (путь из исторической записи; файла в этой копии нет).

1. Владелец открывает Google Search Console → «Проблемы безопасности» для нужного ресурса. Сохранить категорию, дату и примеры URL, удалив токены и персональные данные.
2. По примерам проверить страницы, редиректы, сторонние скрипты, загружаемые файлы, неотслеживаемые файлы сервера и инфраструктуру. Совпадение Git HEAD не исключает компрометацию.
3. Устранить найденную причину; если есть признаки утечки — ограничить доступ и заменить затронутые секреты по отдельному плану.
4. После проверки и устранения отправить запрос на пересмотр через Search Console. Не обещать срок снятия блокировки.
5. Повторно проверить Chrome и сценарий подтверждения на специально созданной тестовой учётной записи.

Не отключать Safe Browsing и не обходить красный экран. Переезд на другой домен или замена действительного сертификата не являются устранением причины.

Официальные справки: [предупреждения Chrome](https://support.google.com/chrome/answer/99020), [Security Issues в Search Console](https://support.google.com/webmasters/answer/9044101).

## Текущий поток подтверждения

Письмо (`../../src/lib/email.ts`; исходник/артефакт не входит в публикацию) строит ссылку из `APP_URL`. Страница (`../../src/app/verify-email/page.tsx`; исходник/артефакт не входит в публикацию) автоматически вызывает API с токеном. API (`../../src/app/api/auth/verify-email/route.ts`; исходник/артефакт не входит в публикацию) проверяет наличие пользователя и срок, записывает `emailVerified`, удаляет токен и срок. Поэтому открытие настоящей ссылки может изменить учётную запись. В документальной сверке 20.10.2026 ссылки не открывались; отдельный тест пользователя 13.10.2026 описан выше.

Повторная отправка (`../../src/app/api/auth/resend-verification/route.ts`; исходник/артефакт не входит в публикацию) заменяет токен и задаёт срок 24 часа. Недействительный или просроченный токен вызывает ошибку приложения, но не объясняет красный экран Chrome.

## Отдельные задачи, не доказанная причина блокировки

- Предлагать повторную отправку письма вместо регистрации заново на странице ошибки.
- Рассмотреть явное подтверждение пользователем и атомарное потребление одноразового токена: сейчас GET изменяет состояние, токен сначала читается, затем обновляется.
- Проверить маскирование query-параметров в логах и referrer-политику. `server.js` сейчас включает `req.url` в сообщение об ошибке; это риск попадания токена в журнал, не доказанная утечка.
- Не публиковать полные ссылки из писем в документации, аналитике и внешних сканерах.

## Ограничения защиты, видимые в коде 20.10.2026

Это результаты чтения исходников, не доказательство эксплуатации и не объяснение классификации Google:

- `src/lib/email.ts` задаёт `tls.rejectUnauthorized: false`: SMTP-сертификат не проверяется. Требуется проверка с провайдером и устранение исключения.
- `GET /api/test-socket-emit` не содержит аутентификационного guard и инициирует board event по taskId. Доступность извне зависит от deployment; маршрут следует закрыть или убрать из рабочего выпуска.
- `POST /api/recurring-tasks/process` проверяет Bearer только при заданном `CRON_SECRET`. При отсутствии переменной обработчик не требует секрет. Не считать эту ветку защищённой по умолчанию; проверить конфигурацию и сделать защиту обязательной.
- Регистрация сохраняет пользователя даже при сбое отправки почты; 201 не доказывает доставку. Повторная отправка заменяет предыдущий токен.
- Вход и общие API имеют разные guards; API Bearer не универсален. См. [матрицу маршрутов](../API.md). Отказы скрытия ресурса могут быть 404.

Исправления кода и проверка конфигурации не выполнялись в рамках актуализации документации. Не публиковать секреты, реальные ссылки подтверждения или содержимое пользовательских задач при проверках.
