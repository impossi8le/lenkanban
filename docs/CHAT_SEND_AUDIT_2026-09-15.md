# Надёжная отправка чата — 15.09.2026

Базовая версия: ffc4da4. Согласованное продолжение — повтор отправки после потери связи/ACK и защита от запоздавших ответов.

## План и границы

1. Воспроизвести сохранённую отправку с потерянным ACK и конкурентный повтор clientId на изолированном PostgreSQL.
2. Сервер: тот же clientId/автор/задача возвращает текущий сохранённый DTO только отправителю, не создаёт второй ряд/уведомление; чужой автор/задача — отказ без утечки.
3. Клиент: ограниченное ожидание, очистка при disconnect/unmount/task change, подтверждённые данные не превращаются в failed от поздней ошибки; повтор вручную с прежним clientId.
4. Независимое review, общий Vitest/typecheck, сборка отдельно от production, публикация на существующий VPS с rollback, smoke встроенным браузером.

## Воспроизведение

Реальный PostgreSQL RED:5failed/1passed в6send integration cases. Повтор после успешного create возвращает InternalError; при конкурентном дубле один ACK ошибочный (оба запроса действительно ожидают PostgreSQL блокировку). Чужой автор/задача не получают корректный ClientIdConflict; повтор изменённого сообщения также ошибочный. Отзыв project access уже работает. Уведомления создаются реальным notifyChatMessage/Prisma, а не мок-счётчиком; отдельный клиент направлен только на тестовую БД.

Клиентская проверка выявила дополнительную потерю черновика: keyboard submit не проверяет соединение перед очисткой текста. Исправляется вместе с attempt lifecycle. Положительный ACK без canonical message:new не считается достаточным для снятия локального ожидания: ограниченный таймер остаётся, затем доступен ручной повтор с тем же clientId.

## Серверное исправление

Preflight clientId lookup и P2002 recovery возвращают сохранённый message:new только исходному автору/задаче после актуальной ACL проверки; текущий текст/вложения не переписываются. Только создатель выполняет broadcast/notify. Добавлена ограниченная валидация неизвестного payload. Серверные unit65GREEN; независимое review без блокеров.

Реальный PostgreSQL GREEN24/24 (6send +5reactions +6read +7move), включая принудительное перекрытие двух INSERT и фактическое единственное уведомление. Container после проверки exactname/label удалён вместе с одноразовой tmpfs-БД, тестовые fixtures воспроизводимы; production kanban_postgres сохранён. Клиентская часть ещё проверяется, релиз не опубликован.

## Клиентское исправление

Ожидание canonical message:new ограничено10с; ACK без DTO не завершает подтверждение. Canonical событие нужного автора/task/clientId сразу завершает ожидание. Disconnect, task change и unmount очищают попытку/таймер/подписки; поздние ответы не влияют на новый запрос или подтверждённую запись. Payload захватывает исходные taskId+generation. Отложенная отправка после смены задачи не попадает в новую задачу, а остаётся failed в исходном cache. Ошибка socket.emit обрабатывается через тот же cleanup. Ctrl+Enter без связи не очищает draft; ручной retry доступен после joined и сохраняет clientId.

Независимое review серверной и клиентской частей без оставшихся блокеров.12 новых send-focused regressions прошли; выполняется полный регрессионный прогон. Ограничения: черновики/неподтверждённые сообщения пока хранятся в памяти клиента, перезагрузка страницы/закрытие браузера не равнозначны сохранённой офлайн-очереди. Автоматический resend не добавлялся.
